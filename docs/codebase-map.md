## Overview

The request flow, in five lines:

1. A client (browser or desktop shell) reaches Tailscale Serve, which terminates TLS and sets the `Tailscale-User-*` headers; the user proxy (nginx) stamps `X-Harmony-Proxy-Secret` and balances over `app1` and `app2` with `least_conn`.
2. Fastify's `onRequest` hook in [`auth/plugin.ts`](../apps/server/src/auth/plugin.ts) authenticates: a bot token decides alone, otherwise `authenticate()` in [`auth/policy.ts`](../apps/server/src/auth/policy.ts) checks the secret, the identity, `ALLOWED_LOGINS` and, for writes and WebSocket upgrades, the `Origin`.
3. A thin route validates input with a zod schema from [`packages/shared`](../packages/shared/src/index.ts) and calls a service, which talks to Postgres through Kysely; changes that bots may hear about write an outbox row in the same transaction.
4. After commit the service publishes the event through `EventBus` to Redis; the `Hub` of every instance (including the one that published) delivers it to its own sockets.
5. In the browser, `RealtimeClient` hands frames to the dispatcher, which feeds `applyFrame` of the zustand store, and components render from the store. The worker meanwhile drains the outbox into signed, retried HTTP calls to bots.

Processes (all but the desktop shell are in [`docker-compose.yml`](../docker-compose.yml)):

| Process             | Entry point                                                | What it does                                                                                                          |
| ------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `app1`, `app2`      | [`server.ts`](../apps/server/src/server.ts)                | Identical Fastify + `ws` instances (`INSTANCE_ID` differs). Serve the API, the WebSocket and the built web client.    |
| `worker`            | [`worker.ts`](../apps/server/src/worker.ts)                | Outbox delivery to bots plus module jobs (`registerWorker`). No proxy secret, no ports; heartbeat file for health.    |
| `migrate`           | [`migrate.ts`](../apps/server/src/migrate.ts)              | One-shot job: core migrations, then each module's. App instances and the worker wait for it to complete.              |
| `nginx`             | [`user.conf.template`](../deploy/nginx/user.conf.template) | User proxy on `127.0.0.1:8470`. Only holder of the proxy secret.                                                      |
| `integrations`      | [`integrations.conf`](../deploy/nginx/integrations.conf)   | Machine ingress on `127.0.0.1:8471`: webhooks, interaction follow-ups and `Authorization: Bot` only; blanks identity. |
| `postgres`, `redis` | [`docker-compose.yml`](../docker-compose.yml)              | State and pub/sub. No published ports. Redis has no persistence.                                                      |
| desktop shell       | [`apps/desktop`](../apps/desktop/README.md)                | Tauri v2 window that loads the server's own origin. Built by its own release workflow, not by the Dockerfile.         |

## Recipes

Every recipe starts from `pnpm build:shared` being current, because server and web read the built `dist` of `@harmony/shared`. Root scripts rebuild it; running `vitest` or `tsc` inside a package does not.

### Add a REST endpoint

1. **Schema in shared.** Add params, query, body and response zod schemas to the right file in [`packages/shared/src`](../packages/shared/src/index.ts) (a new file must be re-exported from `index.ts`). Reuse `Id` for numeric ids.
2. **Route.** Add it to the feature's `routes.ts` (for example [`messages/routes.ts`](../apps/server/src/messages/routes.ts)): `app.get(path, { config, schema: { params, querystring, body, response } }, handler)`. The handler stays thin: read `request.user`, call a service.
3. **Service.** Put the logic in the feature's `service.ts`. Throw `AppError(status, code, message)` for expected failures. Check membership with `channels.requireMember` and rights with `perms.require(user, guildId, key, channelId?)`.
4. **Permission and scope config.** Choose in `config`: `scope: 'messages.read'` (or another `BotScope`, or `'any'`) to let bots in, `humanOnly: true` to keep them out, `public: true` only for token-in-path endpoints. A route with none of these is closed to bots. A new bot scope goes in `BOT_SCOPES` ([`bots.ts`](../packages/shared/src/bots.ts)) and gets a label in [`scopes.ts`](../apps/web/src/components/settings/scopes.ts). A new route file is registered in [`app.ts`](../apps/server/src/app.ts) with its services; a module route uses `ctx.routes` and `config.module` instead.
5. **Client.** Add a method to `api` in [`api/client.ts`](../apps/web/src/api/client.ts) with the response schema, and call it from [`store/actions.ts`](../apps/web/src/store/actions.ts). If other users must see the change live, also add a server event (next recipe).
6. **Protocol doc.** Describe it in [`docs/api/protocol.md`](api/protocol.md) (method, path, auth, errors). A new permission check also goes in the table in [permissions](permissions.md#where-each-key-is-enforced).
7. **Tests.** An integration test in the matching `apps/server/tests/integration/<area>.test.ts` using `api(app, login)` from `support/harness.ts`: success, validation failure, unauthenticated, missing permission, and bot access if it is open to bots. Pure parts get a unit test.

### Add a WebSocket client frame or a server event

Client frame (client to server):

1. Add the object to the `ClientFrame` union in [`protocol.ts`](../packages/shared/src/protocol.ts).
2. Add a `case` to `handle()` in [`realtime/connection.ts`](../apps/server/src/realtime/connection.ts); the switch must stay exhaustive. Call a service method and keep it fast: frames are handled one at a time per socket.
3. Decide on bots: add the frame to `FRAME_SCOPES` in the same file to allow a scope; a frame not listed there is human-only.
4. Send it from the web through `RealtimeClient.send` in an action in [`store/actions.ts`](../apps/web/src/store/actions.ts).
5. Document it under "Client to server" in [protocol](api/protocol.md#client-to-server); test in `frames.test.ts` (parsing) and `realtime.test.ts` (behavior).

Server event (server to client):

1. Add it to `channelEvents` (delivered to subscribed sockets) or `userEvents` (delivered to every socket of one user) in [`protocol.ts`](../packages/shared/src/protocol.ts); `ServerFrame` includes both.
2. Publish it after the transaction commits with `events.toChannel(...)` or `events.toUser(...)` ([`realtime/events.ts`](../apps/server/src/realtime/events.ts)). Never write to a socket directly.
3. Handle it in `applyFrame` in [`store/store.ts`](../apps/web/src/store/store.ts) (and in [`dispatcher.ts`](../apps/web/src/store/dispatcher.ts) if it changes what to subscribe to or refetch).
4. If it changes which presence topics a socket belongs to (joining or leaving a guild or DM), extend `topicChangeFor` in [`presence/scope.ts`](../apps/server/src/presence/scope.ts).
5. A module's frames are named `<moduleId>.<name>`, published with `ctx.publish.channel` or `.user`, and handled by a `frames` entry in the web module ([modules](modules.md#the-web-side)). Bot-visible events are a different mechanism: see [A webhook or embed field](#a-webhook-or-embed-field) and `EVENT_TYPES`.
6. Document it under "Server to client" in [protocol](api/protocol.md#server-to-client).

### Add a database migration

Core (tables the core owns):

1. Create `apps/server/migrations/NNNN_name.ts` with the next number (the last is `0019`; the numbers are not reused) exporting `up(db: Kysely<unknown>)` with raw `sql` template statements, like [`0017_profiles_emoji_perks.ts`](../apps/server/migrations/0017_profiles_emoji_perks.ts).
2. Update the typed table in [`db/schema.ts`](../apps/server/src/db/schema.ts) and the `Database` interface.
3. Never edit or rename an applied migration; write a new one. New columns on busy tables need defaults that do not rewrite the table.
4. Core migrations compile separately (`tsconfig.migrations.json` to `dist/migrations`) and run in the `migrate` job.
5. Test: `migrations.test.ts` applies everything to an empty database; add a case when data must be transformed.

Module (tables only the module uses):

1. Set `migrationsDir: fileURLToPath(new URL('./migrations', import.meta.url))` on the module and add `src/modules/<id>/migrations/0001_name.ts` ([polls example](../apps/server/src/modules/polls/migrations/0001_polls.ts)).
2. The module gets its own history table (`harmony_module_<id>_migration`). Type queries with `trx.withTables<YourTables>()` rather than editing `db/schema.ts`.
3. Modules switched off by `MODULES_DISABLED` are still migrated, so the schema is always complete.

Either way: back up the database first on a live system, and remember that the migration runs once, in the `migrate` container, before the new app instances start ([Deploy a change](#deploy-a-change)).

### Add a user setting

1. Add the field to `appearanceShape` or `behaviorShape` and to `DEFAULT_APPEARANCE` or `DEFAULT_BEHAVIOR` in [`settings.ts`](../packages/shared/src/settings.ts). Settings are stored as JSON and normalized field by field with defaults (`normalizeSettings`), so **no migration** is needed and old rows keep working.
2. Nothing changes in [`settings/service.ts`](../apps/server/src/settings/service.ts) or its routes unless the field needs validation beyond its zod type (custom CSS does).
3. Add the control to the settings page: [`BehaviorPage.tsx`](../apps/web/src/components/settings/BehaviorPage.tsx) or [`AppearancePage.tsx`](../apps/web/src/components/settings/AppearancePage.tsx), using [`controls.tsx`](../apps/web/src/components/settings/controls.tsx); read it with `useBehavior()` or `useAppearance()` from [`store/settings.ts`](../apps/web/src/store/settings.ts).
4. An appearance field that must change the page is applied in `applyAppearance` ([`lib/appearance.ts`](../apps/web/src/lib/appearance.ts)) as a `data-*` attribute or inline property, with CSS keyed on it.
5. Document it in [customization](customization.md) or [theming](theming.md#switches-on-html); update [protocol](api/protocol.md#settings-and-themes) if the API shape is described there; extend `settings-merge.test.ts` or `customization.test.ts`.

### Add a theme token

1. Add the name to `COLOR_TOKENS` (or `LENGTH_TOKENS`) in [`theme.ts`](../packages/shared/src/theme.ts): this is the allowlist that themes may set.
2. Define it in [`tokens.css`](../apps/web/src/styles/tokens.css) in **all three** places that must stay identical for light: the dark `:root` block, the `@media (prefers-color-scheme: light)` block and `:root[data-theme='light']`. Raw values come from `--palette-*` in [`palette.css`](../apps/web/src/styles/palette.css).
3. Give every built-in theme a value in [`presets.ts`](../packages/shared/src/presets.ts) (or make sure `deriveTokens` produces it); a preset that omits a token falls back to its base through `completeTokens`.
4. Use it in component CSS as `var(--your-token)`, never with a color literal.
5. List it with its meaning in [theming](theming.md); expose it in `TOKEN_GROUPS` in [`lib/themeEditor.ts`](../apps/web/src/lib/themeEditor.ts) if users should edit it.
6. Checks: `styles.test.ts` (web) compares the allowlist to the stylesheet; `theme-validation.test.ts` and `color-contrast.test.ts` (server unit) check validation and contrast.

### Add a permission key

1. Core key: add an entry to `CORE_PERMISSIONS` in [`permissions.ts`](../packages/shared/src/permissions.ts) (`key`, `category`, `channel: true` if overwrites may set it, `description`). If new guilds should grant it to everyone, add it to `DEFAULT_EVERYONE_PERMISSIONS`; existing guilds need a core migration to receive it (see [`0015_roles.ts`](../apps/server/migrations/0015_roles.ts) for how the original set was seeded).
2. Module key: call `ctx.permissions.define('key', 'Description')` in the module's `register` (the key becomes `<moduleId>.key`), and add `<moduleId>.key` to `DEFAULT_EVERYONE_PERMISSIONS` if it should default on.
3. Enforce it in the service, not the route: `perms.require(user, guildId, 'key', channelId?)` (or `ctx.permissions.require` in a module). Check any web UI affordance with `usePermission` ([`hooks/usePermission.ts`](../apps/web/src/hooks/usePermission.ts)); the server check is the real one.
4. If a send-path or hot-path check is added, warm the cache before opening a transaction ([deadlocks](#invariants-and-gotchas)).
5. Document it in [permissions](permissions.md) (keys table and "Where each key is enforced") and add a case to the `cases` table in `permissions.test.ts` (integration).

### Add a module

Follow [Write a module in 15 minutes](modules.md#write-a-module-in-15-minutes). In short: a folder `apps/server/src/modules/<id>/index.ts` exporting `defineModule({...})`; one import and one array entry in [`modules/index.ts`](../apps/server/src/modules/index.ts); optional `migrationsDir`, `guildSettings`, `registerWorker`; shared schemas in `packages/shared/src/modules/<id>.ts` (re-export from `index.ts`); the UI in `apps/web/src/modules/<id>/index.tsx` listed in [`apps/web/src/modules/index.ts`](../apps/web/src/modules/index.ts); an integration test (see `polls.test.ts` and `modules.test.ts`); a row in [modules](modules.md#what-the-shipped-modules-own). Never add work to the send path from a module without running `modules-hotpath.test.ts`.

### Add a slash command

Built-in (answered in-process by the server, tied to a module):

1. In a module's `register`, call `ctx.commands.register({ name, description, options, handler })`; see [`coinflip/index.ts`](../apps/server/src/modules/coinflip/index.ts). The name is reserved: bots cannot register it.
2. The handler returns nothing, or `{ content, embeds?, ephemeral? }`.
3. Options are validated by the shared command-option rules in [`bots.ts`](../packages/shared/src/bots.ts); the web builds the form from them ([`lib/commands.ts`](../apps/web/src/lib/commands.ts), [`CommandFields.tsx`](../apps/web/src/components/CommandFields.tsx)), so no web change is normally needed.
4. Test it in `modules.test.ts` the way "built-in coin flip" does, and add it to [modules](modules.md#slash-commands) if it is a shipped module.

Bot (answered by an external service):

1. The bot registers definitions with `PUT /api/bots/:id/guilds/:guildId/commands` ([`commands/routes.ts`](../apps/server/src/commands/routes.ts), [`commands/registry.ts`](../apps/server/src/commands/registry.ts)); the schema is `CommandDefinition` in shared.
2. Invocation (`POST /api/channels/:id/commands` or the `command.invoke` frame) is handled by [`commands/interactions.ts`](../apps/server/src/commands/interactions.ts), which signs a request to the bot's interactions URL and waits up to `INTERACTION_DEADLINE_MS`; the bot can answer later through the follow-up endpoint.
3. A change to this contract updates [protocol](api/protocol.md#slash-commands), the echo bot in [`examples/echo-bot`](../examples/echo-bot/bot.ts) and `commands.test.ts`.

### Add an environment or config variable

1. App-wide: add it to `ConfigSchema` in [`config.ts`](../apps/server/src/config.ts) with a type and a default; worker-only variables go in `WorkerConfigSchema`; a module's own variables go in its `config` schema (the module reads `ctx.config`). Compose passes unset variables as empty strings, which `parseEnv` treats as absent.
2. Pass it in [`docker-compose.yml`](../docker-compose.yml): `x-app-env` (app, worker and migrate), `x-app-instance-env` (the two app instances only) or the worker's own `environment`. Keep secrets away from the worker and migrate job.
3. Document it in [`.env.example`](../.env.example) (commented out when optional). Not every compose variable is listed there today, so check before assuming a variable is undocumented elsewhere.
4. If the load stack needs a different value, set it in [`deploy/load/compose.load.yml`](../deploy/load/compose.load.yml).
5. Cover validation in `config.test.ts`. A build-time web variable (prefix `VITE_`) is different: it is a Docker build argument, not a runtime variable.

### A webhook preset or template filter

1. A preset is a pure function `(headers, body) => LooseMessage | null` in [`webhooks/presets/`](../apps/server/src/webhooks/presets/index.ts). Read the body with the `obj`, `arr` and `str` helpers in `util.ts` so a surprising shape cannot throw, and return `null` for events that are not worth a message.
2. Add the name to `WEBHOOK_PRESETS` in [`webhook-format.ts`](../packages/shared/src/webhook-format.ts), to `PRESETS`, to the `webhooks_format_check` constraint (a new migration; the old one is append-only), and to `FORMAT_INFO` in [`lib/webhook-formats.ts`](../apps/web/src/lib/webhook-formats.ts).
3. Output goes through `normalizeMessage`, which clamps to the embed limits and defuses mass mentions; do not rely on the preset for either.
4. A new template filter goes in `parseFilter` and `applyFilters` in [`webhook-template.ts`](../packages/shared/src/webhook-template.ts) and `TEMPLATE_FILTERS`; keep the list fixed and data-only (no code), and add hostile-input cases to `webhook-template.test.ts`.
5. Tests: a hand-written payload in `tests/support/webhook-payloads.ts`, a unit test per event, and a case in `webhook-formats.test.ts`. Document it in [integrations](integrations.md#webhook-presets-and-templates).

### A webhook or embed field

1. Add the field to the embed schema in [`embeds.ts`](../packages/shared/src/embeds.ts) (`embedShape`, `EmbedField`, and `EMBED_LIMITS` if it has a size). Keep the Discord names, and keep the lenient input form (`EmbedInput`) separate from the strict stored form (`Embed`).
2. Update `embedChars` if the field counts toward the character budget.
3. Embeds are stored as JSON in the message row (`embeds`), so there is no migration. Bots and webhooks both validate with `EmbedsInput`; the webhook body is in [`bots.ts`](../packages/shared/src/bots.ts).
4. Render it in [`Embeds.tsx`](../apps/web/src/components/Embeds.tsx) using [`lib/embeds.ts`](../apps/web/src/lib/embeds.ts) helpers (`safeHttpUrl`, `embedColor`), and style it with tokens in [`integrations.css`](../apps/web/src/styles/integrations.css).
5. Document it in [protocol](api/protocol.md#incoming-webhooks); tests: `webhook-schema.test.ts`, `webhooks.test.ts`, `Embeds.test.tsx`. For a new sender format, add a payload to `tests/support/kuma-payloads.ts` style fixtures.
6. A new bot event type is different: add it to `EVENT_TYPES` in [`bots.ts`](../packages/shared/src/bots.ts), call `enqueueEvent` in the same transaction as the change (via a service `emit`), label it in [`scopes.ts`](../apps/web/src/components/settings/scopes.ts), and document it under [outgoing events](api/protocol.md#outgoing-events).

### Add a screenshot

1. Start the dev stack and the e2e servers as in the [Testing map](#testing-map).
2. Add a step to [`screenshots.spec.ts`](../apps/web/e2e/screenshots.spec.ts) using its `shot('name')` helper and the seeded book-club data from [`support/seed.ts`](../apps/web/e2e/support/seed.ts) (or `seed-integrations.ts`). Set appearance through the API with `setAppearance`, not localStorage.
3. Run `pnpm screenshots` (sets `E2E_SCREENSHOTS=1`). Files are written to `docs/screenshots/` (override with `SHOTS_DIR`); `docs/screenshots/` is ignored by Prettier.
4. Reference it from the doc with a relative image link and real alt text; `node scripts/check-links.mjs` checks the path. Use only fictional data from the seed.

### Add a load test

1. A new scenario is a k6 script in [`loadtest/k6/`](../loadtest/k6/fanout.js) that reads a world file through `readWorld()` from `lib.js` and uses its env variables (see the header of `fanout.js`).
2. Add a runner next to the others (`loadtest/scripts/run-<name>.sh`, modeled on [`run-fanout.sh`](../loadtest/scripts/run-fanout.sh): host guard, sampler, k6, copy raw output to `loadtest/results/`).
3. Build the world with `node loadtest/scripts/setup.ts --prefix <p> --groups N --members M --out loadtest/.work/world-<p>.json` after `pnpm load:up`.
4. Run on the isolated `harmony-load` stack only (never the real one), keep the raw files, and write the result into [performance](performance.md) with its conditions. Only numbers from a run you have raw output for go in docs ([invariants](#invariants-and-gotchas)).
5. Tear down with `pnpm load:down`.

### Deploy a change

1. Merge to the branch that the live checkout tracks and make sure `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.
2. **Back up the database** if the change includes a migration (a `pg_dump` of the Postgres volume's database; the uploads volume if files matter). Migrations only move forward.
3. Run [`scripts/deploy.sh`](../scripts/deploy.sh) from the repository root. It runs `docker compose up -d --build --remove-orphans`: the image is rebuilt, `migrate` runs to completion first, then `app1`, `app2` and the worker are recreated.
4. The script hashes `deploy/nginx/*` into `.deploy-nginx.sha` and, when it changed, runs `docker compose restart nginx integrations`. Compose does not notice edits to bind-mounted files, so without this the proxies keep running old config.
5. Check `docker compose ps` (the script prints it): all services healthy, `migrate` exited 0. Then `curl http://127.0.0.1:8470/healthz`.
6. Never run `docker compose down -v` against the live stack: it deletes the Postgres and uploads volumes.

## Invariants and gotchas

Each rule says why it exists and what enforces it. "No test" means exactly that; treat review as the enforcement.

| Rule                                                             | Why                                                                                                                                                                                                                                                                                                                 | Enforced by                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The send path stays at 6 SQL statements                          | It is the hottest write. Cutting it from 12 to 6 statements moved the measured saturation point ([performance](performance.md)). Modules must add nothing to it.                                                                                                                                                    | `modules-hotpath.test.ts` counts statements for one send: at most 6, identical with no modules and with the shipped ones, and none touching `guild_modules` or polls. A join added to the message query needs a send-rate run too: planning cost does not show in statement counts.                                                                                                               |
| Never wait on the pool inside a transaction                      | Two real deadlocks: (1) the message reader asked for author nicknames inside the send transaction, so under load every request held one connection while waiting for a second; (2) `createTheme` looked up the `extra_themes` perk inside a transaction holding a row lock. The pool filled and everything stalled. | Convention: do pool work **before** `transaction()`. Send path: `perms.warm(channelId)` first, then the reader uses `cachedNicknames` (never waits). Themes: `perks.has` is resolved before the transaction in [`settings/service.ts`](../apps/server/src/settings/service.ts). No dedicated test; a regression shows up as the integration suite hanging (120 s hook timeouts) or in a load run. |
| No color literals in component CSS                               | Themes are data over tokens; a literal in a component cannot be themed and breaks light mode and custom themes.                                                                                                                                                                                                     | `styles.test.ts` ("has no color literals" for every component stylesheet; also forbids reading `--palette-*`). Only `palette.css` and `tokens.css` may hold colors.                                                                                                                                                                                                                               |
| The token allowlist stays in sync with `tokens.css`              | Themes may only set allowlisted tokens, and a token missing from either side silently does nothing or cannot be themed. The light blocks must stay identical because one is the OS-preference copy of the other.                                                                                                    | `styles.test.ts`: allowlist equals the themeable tokens in the dark block; light overrides every themed token; the two light blocks are identical; presets match the palette.                                                                                                                                                                                                                     |
| nginx bind-mounted config needs a restart                        | Compose recreates containers only when their definition changes, not when a mounted file does. One deploy left every request at 502 for this reason.                                                                                                                                                                | [`scripts/deploy.sh`](../scripts/deploy.sh) hashes `deploy/nginx/*` and restarts `nginx` and `integrations` when it changed. Do not bypass the script for nginx changes.                                                                                                                                                                                                                          |
| Upstreams use `resolve` with a `zone`                            | Without it nginx resolves `app1` and `app2` once at startup; a recreated container (new IP) then answers 502 until nginx restarts.                                                                                                                                                                                  | `common.conf` (`resolver 127.0.0.11 valid=10s`, `server ... resolve`). `nginx.test.ts` starts nginx with the real file; `failover.ts` and `recreate.ts` in `loadtest/scripts` check recreate and kill behavior.                                                                                                                                                                                   |
| Everything is delivered through Redis, even on the same instance | One delivery path means one code path to test, and the sender sees what another instance would see. A "local shortcut" would hide bugs that appear only with two instances.                                                                                                                                         | `EventBus` is the only publisher; `Hub` only delivers what Redis hands it. `multi-instance.test.ts`, `typing.test.ts` (cross-instance relay). Never call `hub.send` from a service.                                                                                                                                                                                                               |
| Caches are invalidated over Redis                                | Permissions, module state, custom emoji and perks are cached in each process. A write on one instance must drop the copy on the other, or it serves stale rights for up to the 5 minute TTL.                                                                                                                        | Writers call `changed()`/`invalidate` which publish to `harmony:permissions:invalidate`, `harmony:modules:invalidate`, `harmony:emoji:invalidate`, `harmony:perks:invalidate`; `app.ts` listens through `hub.listen`. Tests: `permissions.test.ts` and `modules.test.ts` ("second instance"), `profiles-emoji-perks.test.ts` (emoji). Perks have no cross-instance test.                          |
| The Origin check covers writes and WebSocket upgrades            | Identity comes from headers a browser sends automatically, so without it any website could act as the signed-in user (CSRF) or open a socket as them.                                                                                                                                                               | `authenticate()` in [`auth/policy.ts`](../apps/server/src/auth/policy.ts). `auth.test.ts` "Origin checks", `uploads.test.ts` ("requires the Origin header"), `policy.test.ts`. A new write route inherits it; a new entry point must call `authenticate`.                                                                                                                                         |
| Bot requests ignore Tailscale headers                            | A bot token is the whole credential. Falling back to ambient identity would let a bad token act as a human, and skipping the Origin check is safe only because a cross-site page cannot attach `Authorization` without a CORS preflight.                                                                            | Branch order in [`auth/plugin.ts`](../apps/server/src/auth/plugin.ts); `bots.test.ts` ("ignores Tailscale headers entirely", "does not fall back"); `integrations.conf` blanks identity headers (`nginx.test.ts`).                                                                                                                                                                                |
| Outbound URLs go through the SSRF guard                          | The server fetches addresses users choose (bot URLs). Resolving once and connecting to that exact address, never following redirects, caps responses and blocks private ranges unless allowlisted for admin-owned bots.                                                                                             | Only `safeFetch` ([`outbound/safe-fetch.ts`](../apps/server/src/outbound/safe-fetch.ts)) may request a user-supplied URL; `OutboundValidator` is only a save-time check. `ssrf.test.ts`. Do not use `fetch` for these.                                                                                                                                                                            |
| The outbox row is written in the same transaction                | A change and its event must exist together or not at all; a separate write can lose events on a crash or announce changes that rolled back. NOTIFY is queued by the transaction and fires only on commit.                                                                                                           | `enqueueEvent(trx, ...)` takes the transaction. `outbox.test.ts` ("writes no event when the transaction rolls back", "records every event type in the same transaction").                                                                                                                                                                                                                         |
| Only measured numbers in docs                                    | The performance claims are the project's credibility. A guessed or remembered figure is worse than none.                                                                                                                                                                                                            | No test. State conditions with every number, keep raw outputs in `loadtest/results/`, and use words ("not measured") when there is no run. Review.                                                                                                                                                                                                                                                |
| Protocol changes start in `packages/shared`                      | Server and web both compile against it, so drift becomes a type error instead of a runtime surprise.                                                                                                                                                                                                                | TypeScript (`pnpm typecheck`). Remember `pnpm build:shared` first.                                                                                                                                                                                                                                                                                                                                |
| Migrations are append-only and keep their numbers                | Applied migrations are recorded by name; editing or removing one breaks existing databases. Numbers 0007 to 0009 are unused on purpose in the history.                                                                                                                                                              | Kysely's migrator validation; `migrations.test.ts`. Back up before running new ones on live data.                                                                                                                                                                                                                                                                                                 |
| Routes are closed to bots unless they declare a scope            | A forgotten `config` should fail closed.                                                                                                                                                                                                                                                                            | `auth/plugin.ts` returns `bot_not_allowed`; `bots.test.ts` ("keeps human-only endpoints closed to bots").                                                                                                                                                                                                                                                                                         |

Playwright starts its own API on port `18080` and Vite on `15173` ([`playwright.config.ts`](../apps/web/e2e/playwright.config.ts)), with `PERKS_DEFAULT=none`, raised rate limits and a private-address allowlist for the echo bot.

**e2e and screenshots.** Install the browser once with `pnpm --filter @harmony/web exec playwright install chromium`. `DevApi` in `e2e/support/dev-api.ts` makes API calls as a user; `seedBookClub` and `seedIntegrations` create fictional data. `pnpm screenshots` runs only `screenshots.spec.ts` and rewrites `docs/screenshots/*.png`. Use unique names per run when a test clicks something in a shared channel.

## Glossary

| Term               | Meaning in this codebase                                                                                                                                                      |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Guild              | A "server" in the UI: a community with channels, members and roles. The code, API and tables say `guild`.                                                                     |
| Channel, DM        | A text channel inside a guild, or a direct-message channel (`kind: 'dm'`, no guild, no roles). Both are rows in `channels`.                                                   |
| Instance admin     | The first user to sign in (`isAdmin`). Can grant perks and own bots that reach private addresses. Not the same as a guild owner.                                              |
| Role, position     | A named set of permission keys with a color and an order; a higher position outranks a lower one (hierarchy rules in [permissions](permissions.md#hierarchy-rules)).          |
| Overwrite          | A per-channel allow or deny list for one role or member, applied on top of guild-wide roles.                                                                                  |
| Permission key     | A string such as `send_messages` (core) or `polls.create` (module).                                                                                                           |
| Module             | A feature folder registered through `defineModule`, with optional routes, frames, commands, tables, settings and UI. Optional ones can be switched off per guild.             |
| `MODULES_DISABLED` | Instance-wide switch-off list, by module id.                                                                                                                                  |
| Perk               | An admin-grantable capability for a user (for example `larger_uploads`); `PERKS_DEFAULT` decides what everyone has.                                                           |
| Outbox             | The `event_outbox` table: events written in the same transaction as the change, then delivered to bots by the worker with retries. `event_deliveries` holds per-bot attempts. |
| Delivery           | One attempt chain of one event to one bot's events URL; ends `succeeded`, or `dead` after the maximum attempts.                                                               |
| Interaction        | A slash command invocation sent to a bot (signed) and answered or followed up within a deadline.                                                                              |
| Ephemeral          | A reply shown only to the caller (`interaction.ephemeral` frame), not stored as a message.                                                                                    |
| Ingress            | The `integrations` proxy that only machines use. The _user proxy_ is the other one.                                                                                           |
| Proxy secret       | The shared value nginx stamps on user traffic so the app knows the request passed through it.                                                                                 |
| Topic              | A Redis pub/sub channel: `harmony:channel:<id>`, `harmony:user:<id>`, `harmony:presence:guild:<id>`, `harmony:presence:dm:<id>`, plus the invalidation topics.                |
| Hub                | Per-instance registry of sockets and rooms that turns Redis messages into WebSocket frames.                                                                                   |
| Frame              | One JSON WebSocket message. Client frames are `ClientFrame`; server frames are `ServerFrame`; module frames are named `<moduleId>.<name>`.                                    |
| Backfill           | The messages sent after `subscribe` with `lastSeenId`, so a reconnecting client catches up. The client dedupes by message id.                                                 |
| Nonce              | A client-chosen id on a sent message; the server echoes it in the ack and the broadcast so the client matches its pending message.                                            |
| Marker, decorator  | A message's `modules` column names the modules that attached data; the module's decorator loads that data in one batch per page.                                              |
| Domain event       | An in-process, after-commit notification for modules (`message.created`, ...). Not the outbox and not Redis.                                                                  |
| Token (theme)      | A CSS custom property such as `--color-bg-panel`. _Primitives_ are `--palette-*`; _semantic tokens_ are what components use.                                                  |
| Safe mode          | `?safe` in the URL: custom themes and CSS are ignored so a broken theme cannot lock someone out.                                                                              |
| World              | A load-test layout of users, guilds and channels created ahead of a run and stored as JSON.                                                                                   |
