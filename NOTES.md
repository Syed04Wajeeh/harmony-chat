# Engineering notes

## Decisions

- 2026-10-21: Raw `ws` over Socket.IO. The protocol is small and typed with zod; Socket.IO's rooms, fallbacks and custom framing add weight and hide behavior I want to own. Rejected: Socket.IO.
- 2026-10-21: Kysely over Prisma. Migrations and queries stay close to plain SQL, no generated client or query engine binary, and the Docker image stays small. Rejected: Prisma.
- 2026-10-21: pnpm monorepo with a shared zod package. Client and server validate against the same schemas, so protocol drift is a compile error. `@harmony/shared` is built with `tsc` to `dist` and consumed as a normal package (`main`/`types`/`exports`); this works unchanged for Vite, the Node server and `pnpm deploy` in Docker. Rejected: source exports (Node cannot run `.ts` from `node_modules`) and project references (extra config for no gain here).
- 2026-10-21: Migrations run in a separate one-shot `migrate` compose service, so several app instances never race on the schema. Rejected: migrating on app startup.
- 2026-10-21: The app serves the built web client itself, so client and API share one origin. That keeps CORS out of the picture and simplifies Origin checks for WebSockets later. Rejected: separate static host.
- 2026-10-21: TypeScript pinned to 6.x. typescript-eslint does not support TypeScript 7 yet, and one version across the workspace avoids running two compilers.
- 2026-10-21: Identity comes from Tailscale Serve headers, and a shared secret proves the request came through nginx. Serve strips client-supplied `Tailscale-User-*` headers, but any other container on the Docker network can reach `app:8080` directly and send whatever headers it likes. nginx therefore stamps `X-Harmony-Proxy-Secret` on every proxied request (overwriting client values), and the app rejects anything without it (constant-time compare). Rejected: trusting the network boundary alone, and mTLS between nginx and app (more moving parts for the same guarantee here).
- 2026-10-21: Identity is ambient (the browser attaches it to every request), so state-changing requests and WebSocket upgrades must carry an `Origin` equal to `PUBLIC_ORIGIN`; a missing Origin is rejected. This blocks cross-site form posts and cross-site WebSocket hijacking from any page the user happens to visit. Rejected: CSRF tokens (needs session state and client plumbing, and Origin is already sent by every browser on these requests) and `SameSite` cookies (there are no cookies).
- 2026-10-21: Every message delivery goes through Redis pub/sub, including to sockets on the same instance. One delivery path means a second app instance needs no new code, and the two-instance integration test exercises exactly the production path. Rejected: a local fast path with Redis only for other instances (two paths to keep consistent, and the local one would hide cross-instance bugs).
- 2026-10-21: On `subscribe` with `lastSeenId`, the server joins the Redis channel first and only then queries Postgres for newer messages. A message published between the two steps is delivered live and also appears in the backfill; the client dedupes by id. The reverse order would lose any message committed after the query but published before the subscribe. Backfill is capped at 200 rows; with `hasMore` the client refetches the newest page rather than splicing a gap. `backfill` is also sent (empty) when no `lastSeenId` is given, so it doubles as the subscription confirmation.
- 2026-10-21: Clients send a random `nonce` with each message and render it optimistically. The server answers the sender with `ack {nonce, message}` and the broadcast also reaches the sender's socket as `message.created`. Both carry the same message id, and the client keeps messages keyed by id, so whichever arrives first wins and the pending entry is dropped on ack. Rejected: suppressing the broadcast to the sending socket (needs per-socket tracking across instances, and other tabs of the same user still need the message).
- 2026-10-21: Per-user message rate limit is a fixed window in Redis (`INCR` plus `EXPIRE NX` in one `MULTI`), shared by REST and WebSocket sends; general REST traffic uses `@fastify/rate-limit` with the same Redis. Fixed windows allow up to 2x the limit across a window boundary, which is fine for chat spam control. Rejected: sliding-window log (a sorted set per user, more memory and commands), token bucket in Lua (more code to own), and in-process counters (wrong as soon as there are two instances). The HTTP limiter fails open if Redis is down.
- 2026-10-21: User rows are upserted from the identity headers, with a 60 second in-process cache keyed by login. A request only touches the database when the cache is cold or the display name or avatar changed. The cache is per instance and bounded, and a changed profile is written through immediately because the cache entry only counts as a hit while the values match. Rejected: an upsert per request (a write on every API call) and a Redis-backed cache (another network hop to save a primary-key read).
- 2026-10-21: nginx sits between Tailscale Serve and the app and is the only published port (`127.0.0.1:8470`). Its config is a template rendered by the official image's envsubst step, restricted to `PROXY_*` variables so nginx's own `$variables` are never touched. The upstream is an `upstream` block so a second app instance is one more `server` line.
- 2026-10-21: In development, `DEV_AUTH_LOGIN` substitutes a fixed identity and skips the proxy secret. `loadConfig` refuses to start if it is set under any `NODE_ENV` other than `development`, so a stray variable cannot open a production deployment.
- 2026-10-21: Verified Tailscale Serve's header behavior before relying on it, from the v1.102.3 source (`addTailscaleIdentityHeaders`) and live tests: it deletes client-sent `Tailscale-User-*` headers on every request, sets them only for untagged user nodes, and RFC 2047-encodes non-ASCII names. Full write-up in `docs/security/trust-model.md`.
- 2026-10-21: The server's `message.created` broadcast carries the sender's nonce, so the sending client reconciles its optimistic copy whichever of `ack` or the broadcast arrives first.
- 2026-10-21: Harmony's containers opt out of the host's Watchtower auto-updates via label. Images are pinned and upgraded deliberately.
- 2026-10-22: Servers are called `guilds` in code, the database and the API (Discord's term), and "servers" only in the UI, so they are never confused with the backend server. Any signed-in user can create a guild and becomes its owner; `users.is_admin` is only an instance-level moderation override (it can delete/rename any guild and moderate messages) and is never required to create guilds or channels. The first user ever created is admin, decided inside the insert transaction under a Postgres advisory lock so two simultaneous first logins cannot both win; a migration backfill promotes the lowest existing id.
- 2026-10-22: Access is `channel_members` rows, kept in step with guild membership on purpose. Joining a guild inserts one row per non-private channel, creating a public channel inserts a row per guild member, leaving a guild deletes the user's rows for that guild's channels. That is write fan-out (cost grows with channels per guild on join and members per guild on channel create) in exchange for one uniform rule everywhere: "you can read a channel iff you have a row". Authorization, unread counts and the live-subscription check are single indexed lookups with no guild/visibility logic or joins. Rejected: deriving access from `guild_members` plus a visibility rule (every history, search, unread and WebSocket check would need the union of two sources, and the unread query would join guilds) and storing read state in a separate table (a second row per user per channel to keep in sync).
- 2026-10-22: Text channel names are unique per guild (`unique (guild_id, name)`); `guild_id` is null only for DMs, enforced by a check constraint together with the name and `dm_key` shape. A guild named "Harmony" is flagged `is_default` (one row, partial unique index); the migration creates it from existing data owned by the earliest user and moves `general` and its messages into it. Newcomers join the default guild on their first request; the very first user on an empty database creates it. Rejected: leaving new users guild-less (an empty first screen) and a hard-coded guild id.
- 2026-10-22: A non-member gets `403 forbidden` for anything that exists, `404` only for ids that do not. Hiding existence behind 404 would buy nothing because ids are sequential. Public channels can no longer be joined or left individually (that browse feature was dropped for guild membership); private channels can be left. Removing someone from a private channel needs the channel creator, guild owner or an admin who is a member of it; admins do not get read access to channels they are not in.
- 2026-10-22: Invite use-counting is one conditional `UPDATE ... SET uses = uses + 1 WHERE (expires_at is null or expires_at > now()) and (max_uses is null or uses < max_uses)`, inside the transaction that inserts the membership. Concurrent accepts serialize on the row lock, so `max_uses` cannot be exceeded; the membership insert runs first and a user who is already in the guild consumes nothing, which also makes double-clicks harmless. Tested with 10 simultaneous accepts of a 3-use invite. Rejected: read-then-write in the application (races) and advisory locks (the row lock is already enough).
- 2026-10-22: DM channels are created idempotently through `dm_key = "<minUserId>:<maxUserId>"` with a unique index and `INSERT ... ON CONFLICT (dm_key) DO NOTHING`, then a select on conflict. Two people starting a DM at the same moment get the same channel without any locking or retry loop. DMs are only allowed between users who share a guild, so a stranger cannot be messaged. Rejected: looking up "a channel with exactly these two members" (needs a group-by query and still races) and a separate DM table (the message, unread and WebSocket code would have to handle two kinds of channel).
- 2026-10-22: A per-user Redis topic (`harmony:user:<id>`), reference-counted per instance like channel topics. Events that concern a user rather than a channel (`channel.joined/removed/updated`, `guild.*`, `read.updated`, `mention`) are published once and reach every session of that user on every instance. `channel.removed` also makes the hub drop that user's live subscription to the channel, so losing membership ends delivery immediately and not only on the next `subscribe`. Rejected: pushing these over the channel topic (a sidebar needs events about channels the user is not subscribed to) and polling `GET /api/channels`.
- 2026-10-22: Unread counts. `GET /api/channels` computes, per channel the user is in, `max(id)` from `messages` (index `(channel_id, id desc)`), and two counts each from a subquery with `LIMIT 100`: messages with `id > coalesce(last_read_message_id, 0)` that are not mine and not deleted (range scan of the same index), and rows in `message_mentions` for me with `message_id > last_read` (new index `(user_id, message_id)`; the id bound is repeated on `message_mentions` because Postgres does not derive inequality bounds across a join). `count(*)` over a `LIMIT 100` subquery means a channel with 50,000 unread costs the same as one with 100, and `100` is reported as "100 or more". Guild badges sum the already-capped channel numbers and cap again. Read markers use `greatest(last_read_message_id, $new)` (`greatest` ignores NULL) so a stale tab can never move them back; the new id must be a message in that channel, otherwise a client could mark the future as read. People who join a channel start at its latest message. Rejected: exact counts (an unbounded scan per channel per page load), a denormalized unread counter (needs updating for every member on every message and drifts on delete), and a bound on `m.id` only without the `LIMIT`.
- 2026-10-22: Presence is a Redis sorted set per user (`harmony:presence:<id>`, member = connection id, score = expiry in ms) plus a set of user ids currently marked online. One Lua script performs add/refresh, remove and expire and returns whether the user flipped (`1` came online, `-1` went offline, `0` nothing). The marker set, not the ZSET size, is the source of truth, so the flip is decided atomically inside Redis and exactly one caller sees it, however many instances, tabs and sweepers race. Time comes from Redis `TIME`, so instances with skewed clocks agree on expiry. Each socket refreshes every 30 s with a 90 s TTL; every instance also sweeps all online users every 30 s, which turns a crashed instance's connections into one `offline` event within about two minutes. Transitions are published on `harmony:presence` and delivered to every connected client; `invisible` is published as `offline`. At this size that is a handful of users, so there is no scoping. At larger scale presence would be scoped to users who share a guild or DM with the viewer (maintain the viewer's set of peers per connection and filter on dispatch). Rejected: relying on the socket `close` event (misses crashes and network drops), Redis key expiry notifications (not delivered reliably and give no atomic transition), a per-connection key with TTL (cannot tell "last connection gone" atomically), presence rows in Postgres (a write per heartbeat), and a single elected sweeper (needs leader election; running the sweep everywhere and trusting the script's result is simpler and idempotent). Known gap: the Redis publish happens after the script returns, so two rapid flips from different instances could in theory be published out of order; clients refetch `GET /api/presence` on reconnect.
- 2026-10-22: Typing pings are ephemeral. A client frame is throttled with `SET key 1 PX 2000 NX` in Redis (one relay per user and channel every 2 s across all of the user's tabs and all instances) before the membership check, so a flood costs one Redis command. The relay is published on the channel topic and never stored; clients expire the indicator after about 6 s. All WebSocket frames also pass an in-process token bucket per socket (30 frame burst, 3 per second refill; extra frames get `rate_limited`, a socket that keeps going after 100 drops is closed with 1008). In-process is correct here because the budget is per connection, which lives on one instance. REST write limits (messages, reactions, uploads) stay fixed-window counters in Redis, shared by REST and WebSocket.
- 2026-10-22: Deleting a message is a soft delete (`deleted_at`). The row stays so replies keep their parent and reaction/mention/pin rows stay consistent; the API serves a tombstone (`deleted: true`, empty content, no attachments, reactions or mentions). Tombstones stay in history pages and backfill so keyset pagination has no holes and a client that missed the `message.deleted` event still learns about the delete when it reloads. Deleted messages are excluded from search, unread counts and pins. Files of deleted messages stay on disk until the guild is deleted. Rejected: hard delete (breaks reply links, loses audit trail) and removing the row from history (clients cannot tell a gap from a delete).
- 2026-10-22: Uploads stream to a `Storage` interface (`put/get/delete`; `LocalDiskStorage` writes `<key>.partial` and renames, so a failed or oversized upload leaves nothing). Size and SHA-256 are computed while streaming; the stream is piped with `pipeline`, not `.pipe`, so the multipart size-limit error reaches the writer and the partial file is removed. The content type comes from the file's magic bytes (`file-type`), never from the client; anything it does not recognise, including SVG and HTML, is stored as `application/octet-stream`. On download, only png/jpeg/gif/webp are `Content-Disposition: inline`; everything else is `attachment`, with `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and `Cache-Control: private, max-age=31536000, immutable` (the URL contains the immutable attachment id). Filenames are reduced to a basename without control, bidi or shell/markup characters. Access follows the message's channel (the uploader until attached; guild icons are visible to any signed-in user so invite previews work). Unattached uploads older than 24 hours are deleted by an interval job guarded by a Redis `SET NX PX` lock, which expires on its own so a crashed holder never blocks the next run; the job deletes rows first (never a row pointing at a missing file) and skips icons still referenced by a guild. nginx allows `client_max_body_size 11m` only on `location = /api/uploads`. Rejected: trusting `Content-Type` or the extension, serving SVG inline (script execution on the app origin), object storage in this phase (the interface is the seam for it), and a database lock for the cleanup job.
- 2026-10-22: Search uses Postgres full text with a generated, stored `tsvector` (`to_tsvector('simple', content)`) and a GIN index, queried with `websearch_to_tsquery('simple', q)`. The `simple` configuration only lowercases and splits on word boundaries: chat is multilingual and full of names, code and slang, and the `english` configuration would stem words ("running" matches "run") and drop stop words, which is wrong for non-English text and surprising for exact names. The cost is no stemming; users type the word they want. The membership join is part of the query, so messages from channels the caller cannot read can never match. Pagination is keyset on message id, newest first. Rejected: `ILIKE '%q%'` (sequential scan), an external search engine (another service to run for a homelab), and `english`.
- 2026-10-22: Mentions are `<@userId>` tokens written by the client. The server parses them, keeps only users who are members of that channel (and not the author), stores `message_mentions`, and notifies only newly mentioned users when a message is edited. Client-supplied token text is never trusted for notification; membership is checked on the server.
- 2026-10-22: History pages, search results and pins are hydrated in four queries regardless of page size (messages joined with author and reply parent, then reactions, attachments and mentions each fetched with `= any($ids)`). A test counts the SQL statements for a 1-message and a 31-message page and requires them to be equal.
- 2026-10-22: Web state lives in one zustand store (`apps/web/src/store`) with normalized records keyed by id (users, guilds, channels, per-channel history, outbox, typing, presence), and a single dispatcher that feeds it from REST and from `ServerFrame`s. `applyFrame` is a plain switch over the protocol's frame types, so the store is tested by feeding it frames, without React or a socket. Transient UI (toasts, drawers, jump requests) is a second tiny store so it cannot cause message-list renders. Rejected: Redux Toolkit (more ceremony for the same shape), React Query (the WebSocket is the source of truth for most data and cache invalidation would fight it), and per-hook `useReducer` state as in Phase 1 (could not drive sidebar badges or the title from events for channels that are not open).
- 2026-10-22: The client subscribes to every channel it can see, not only the open one, because channel events (and so unread counts) only arrive for subscribed channels. The dispatcher sends the first 15 `subscribe` frames at once and the rest at one per 400 ms, staying inside the socket's 30-frame bucket (3 per second refill), and the open channel goes first. `lastSeenId` is the newest cached message, else the channel's `lastMessageId`, so channels that were never opened get an empty backfill. Messages are cached only for channels that were opened; live events for others only update the summary, so a cache is never a partial list. On reconnect idle caches are dropped (edits and deletes are not in a backfill), the active channel refetches its newest page, and a backfill with `hasMore` drops the cache so the open view reloads.
- 2026-10-22: React Router (`react-router`, declarative `BrowserRouter`) for `/channels/:guildId/:channelId`, `/channels/@me/:dmId` and `/invite/:code`. The URL is the single source of truth for which guild and channel are open, so reload, back button and shared links work; the last channel per guild is remembered in localStorage only to pick where the guild rail goes. Rejected: keeping the selection in the store (no deep links) and a data router with loaders (data arrives over the socket, so loaders would add nothing).
- 2026-10-22: Message text is rendered by a small hand-written tokenizer (`lib/markdown.ts`) that produces a tree, and React elements are made from that tree. There is no HTML string anywhere and no `dangerouslySetInnerHTML`, so React's escaping is the only output path. Only `http:` and `https:` URLs become links (checked with `new URL`), `[text](url)` links are not supported at all, and nesting depth is capped. Rejected: marked + DOMPurify. It would be a larger dependency, would parse the full CommonMark surface (images, raw HTML, reference links) only to strip most of it again, and puts the safety of every message on a sanitizer configuration; a tokenizer that cannot express the dangerous constructs has nothing to bypass. The cost is that unusual Markdown (lists, headings, tables) shows as plain text.
- 2026-10-22: Mentions stay `<@id>` on the wire. The composer shows `@Name`, keeps a `@Name -> id` map for names picked from autocomplete, and converts on send with one regex over the known names (whole-word match, longest first); editing decodes the tokens back. Names the user typed by hand or edited are plain text, which matches the server's rule that only real members count. Known limit: two members with the same display name cannot be told apart in one message.
- 2026-10-22: Mobile is designed as the primary layout, below 900px: a full-screen chat, a left drawer holding the guild rail and channel list, a right drawer with members, and a bottom sheet for message actions (long-press instead of hover). Drawers are driven by `--pl` / `--pr` CSS variables (0 closed to 1 open) that the touch handlers write directly during a drag, so a swipe causes no React renders; an axis lock gives up on vertical gestures at once and the shell sets `touch-action: pan-y` so scrolling is never fought. Closed drawers are `inert`. The app root is `position: fixed` and sized from `visualViewport` (`--app-height`, `--app-top`), so the composer rides above the on-screen keyboard on iOS, where `100dvh` does not shrink; dialogs placed as sheets use the same variables. Enter inserts a newline on `(pointer: coarse)` devices and the send button sends. Rejected: a CSS-only responsive squeeze of the desktop grid, and a UI library (the touch behaviors are the product here).
- 2026-10-22: PWA through a web manifest and icons only (standalone display, theme color equal to the dark background token, SVG plus rasterized 192/512/maskable/apple-touch PNGs), with no service worker. Offline support would need a cache-invalidation story for the app shell and would not make chat useful offline; installability and the app-like window were the goal. The manifest cannot read CSS variables, so its colors are copied from the tokens.
- 2026-10-22: All colors, radii, spacing and fonts are CSS custom properties on `:root`; dark is the default and the light theme is the same tokens under `prefers-color-scheme: light`. Components contain no color literals (avatar tones are `--tone-N` variables picked by id hash), so Phase 5 user themes only have to override tokens. Radix primitives (dialog, alert dialog, dropdown menu, popover) provide focus handling, Escape and ARIA; everything visual is plain CSS.
- 2026-10-22: Development-only `dev_login` cookie: a dev-mode server (`NODE_ENV=development` and `DEV_AUTH_LOGIN` set) lets a browser choose its identity among `@example.com` logins, so one Playwright run can be several users. It is gated by the dev policy (production never builds one), restricted to a reserved domain and still subject to the allowlist and Origin check; see the trust model's "Development mode". Rejected: a header (browsers cannot set headers on WebSocket upgrades) and a separate test-only server build (a second code path to keep honest).
- 2026-10-22: Dev and e2e infrastructure never touch the production stack: a `harmony-dev` compose project (`compose.dev.yml`, tmpfs Postgres on 127.0.0.1:15432, Redis on 16379) and ports 18080 / 15173 for the API and Vite. The e2e suite lets Playwright start the API and Vite itself and runs in CI against service containers; the screenshots are a separate Playwright project (`E2E_SCREENSHOTS=1`) that seeds a fictional data set.

## Measured results

Only numbers actually measured, with conditions.

- 2026-10-21, live through Tailscale Serve: a forged `Tailscale-User-Login` header was replaced with the caller's real login; POST without `Origin` → 403, foreign `Origin` → 403; WebSocket upgrade with own origin → 101, foreign origin → 403; direct connection to the tailnet IP on the backend port refused. Two WebSocket clients: sender received `ack` + `message.created`, the other client received `message.created`.
- 2026-10-21: test suite at end of Phase 1: 66 unit tests, 41 integration tests (Testcontainers Postgres + Redis), all passing.

- 2026-10-22, end of Phase 2a: 138 unit tests and 132 integration tests (Testcontainers Postgres, Redis and nginx), all passing in five consecutive full integration runs after the last fix. One typing test was flaky in an earlier run because it compared global message counts while other test files inserted messages; it now checks its own channel.
- 2026-10-22, live stack after `docker compose up -d --build`: the four new migrations applied to the existing database (one real user and two messages): that user stayed admin and became owner of the new default guild "Harmony", `general` moved into it with its messages intact. Through nginx on 127.0.0.1:8470 a throwaway user was added to the default guild, uploaded a 1x1 PNG declared as `text/html` (stored as `image/png`, 1x1), downloaded it with the expected hardened headers, posted and deleted a message; the throwaway rows, file and Redis keys were then removed.
- 2026-10-22, end of Phase 2b: 146 server unit tests, 86 web unit tests (Vitest, Testing Library), 132 integration tests, 7 Playwright e2e tests (Chromium; desktop and an iPhone-sized touch profile), all passing. The e2e suite passed in four consecutive full runs after the last fix; one earlier run had a single unexplained failure in the two-user test that did not recur.

## Problems solved

- `pnpm fetch` failed in Docker with `ERR_PNPM_IGNORED_BUILDS`: pnpm 12 refuses to continue when dependencies have unapproved install scripts. Fixed by declaring `allowBuilds` in `pnpm-workspace.yaml` (esbuild allowed; cpu-features, protobufjs and ssh2 from Testcontainers denied).
- ESLint crashed at startup with "typescript-eslint does not support TS 7.0". Pinned TypeScript to 6.x across the workspace.
- `Migrator` and `FileMigrationProvider` are no longer exported from the `kysely` root in 0.29; they are imported from `kysely/migration`.
- Kysely's `FileMigrationProvider` dynamic-imports migration files, which needs file URLs under ESM, and the production image only has compiled JS. Migrations are compiled to `dist/migrations` by a second `tsc` pass, and the migrator uses that folder when present, else `migrations/` from source.
- A rejected WebSocket upgrade (bad Origin, no identity) left its socket open, so `app.close()` hung until the test hook timed out. `@fastify/websocket` marks a request as an upgrade in its own `onRequest` hook and destroys the raw socket in `onResponse` only if that flag is set; my auth hook, registered earlier, threw before the flag was set. Registering the websocket plugin before the auth plugin fixed it.
- nginx returned 403 `proxy_required` for every proxied request even though the secret was rendered correctly: `proxy_set_header` directives are inherited by a location only if the location declares none, and the WebSocket location declared two. All `proxy_set_header` lines now live at server level and the locations add none.
- The production image crashed on start with `Cannot find package 'ws'`: it was only a dev dependency, but the hub imports it at runtime. Moved to `dependencies`.
- The nginx integration test first put the real app behind nginx with `host-gateway`; every proxied request timed out because the host firewall drops traffic from containers to host ports. The test now runs the real template against a second nginx container that echoes the headers it received, on a private Docker network, which exercises the exact thing under test (what nginx forwards, and the body-size limits per location) without depending on host networking.
- After `docker compose up -d --build` the new `/api/uploads` location was not live: nginx only renders its template at container start and the template is a bind mount, so compose saw no change and kept the old container. `docker compose restart nginx` is needed after editing the template.
- Long-pressing a message opened the action sheet, which closed again when the finger lifted: the release produced a click on the full-screen overlay, which counted as an outside tap, or landed on a sheet action. The sheet now ignores outside interaction and pointer events for its first 600 ms (`graceMs`, a CSS `guard` animation for `pointer-events`). Found by the mobile e2e test, not by the desktop-sized screenshots.
- `**bold *italic***` rendered as bold text with stray asterisks: the search for a closing `**` stopped at the first two characters of the closing `***`. A two-character closer now closes on the last two characters of a longer run.
- The left drawer's shadow showed as a dark strip on the screen edge while the drawer was closed (translated off-screen but its blur reaches in). The shadow is only applied while a drawer is open or being dragged.
- The Playwright image's `system-ui` resolves to a font without a bold face, so every screenshot looked flat. The screenshot run injects a font that has bold; real devices are unaffected.
- A Playwright worker restart after a failed test re-ran `beforeAll`, which seeded the whole data set twice (duplicate server in the rail). Fixed by making the failing steps robust and resetting the database before each screenshot run.
- React 19's lint rules (`react-hooks/refs`, `set-state-in-effect`) rejected patterns that are common in older code, such as mirroring state into a ref during render and resetting state inside an effect. Refs are now updated in effects, and reset state is derived or reset by remounting.
- `useUi((s) => s.setDrawer)` tripped `unbound-method` because the store interface declared methods; actions are declared as function properties.
