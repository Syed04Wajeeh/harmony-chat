# Engineering notes

## Decisions

- 2026-10-21: Raw `ws` over Socket.IO. The protocol is small and typed with zod; Socket.IO's rooms, fallbacks and custom framing add weight and hide behavior I want to own. Rejected: Socket.IO.
- 2026-10-21: Kysely over Prisma. Migrations and queries stay close to plain SQL, no generated client or query engine binary, and the Docker image stays small. Rejected: Prisma.
- 2026-10-21: pnpm monorepo with a shared zod package. Client and server validate against the same schemas, so protocol drift is a compile error. `@harmony/shared` is built with `tsc` to `dist` and consumed as a normal package (`main`/`types`/`exports`); this works unchanged for Vite, the Node server and `pnpm deploy` in Docker. Rejected: source exports (Node cannot run `.ts` from `node_modules`) and project references (extra config for no gain here).
- 2026-10-21: Migrations run in a separate one-shot `migrate` compose service, so several app instances never race on the schema. Rejected: migrating on app startup.
- 2026-10-21: The app serves the built web client itself, so client and API share one origin. That keeps CORS out of the picture and simplifies Origin checks for WebSockets later. Rejected: separate static host.
- 2026-10-21: TypeScript pinned to 6.x. typescript-eslint does not support TypeScript 7 yet, and one version across the workspace avoids running two compilers.
- 2026-10-21: Identity comes from Tailscale Serve headers, and a shared secret proves the request came through nginx. Serve strips client-supplied `Tailscale-User-*` headers, but any other container on the Docker network can reach `app:8080` directly and send whatever headers it likes. nginx therefore stamps `X-Harmony-Proxy-Secret` on every proxied request (overwriting client values), and the app rejects anything without it (constant-time compare). Rejected: trusting the network boundary alone, and mTLS between nginx and app (more moving parts for the same guarantee here).
- 2026-10-21: Identity is ambient (the browser attaches it to every request), so state-changing requests and WebSocket upgrades must carry an `Origin` equal to `PUBLIC_ORIGIN`; a missing Origin is rejected. This blocks cross-site form posts and cross-site WebSocket hijacking from any page the user happens to visit. Rejected: CSRF tokens (needs session state and client plumbing, and Origin is already sent by every browser on these requests) and `SameSite` cookies (there are no cookies).
- 2026-10-21: Every message delivery goes through Redis pub/sub, including to sockets on the same instance. One delivery path means a second app instance needs no new code, and the two-instance integration test exercises exactly the production path. Rejected: a local fast path with Redis only for other instances (two paths to keep consistent, and the local one would hide cross-instance bugs).
- 2026-10-21: On `subscribe` with `lastSeenId`, the server joins the Redis channel first and only then queries Postgres for newer messages. A message published between the two steps is delivered live and also appears in the backfill; the client dedupes by id. The reverse order would lose any message committed after the query but published before the subscribe. Backfill is capped at 200 rows; with `hasMore` the client refetches the newest page rather than splicing a gap. `backfill` is also sent (empty) when no `lastSeenId` is given, so it doubles as the subscription confirmation.
- 2026-10-21: Clients send a random `nonce` with each message and render it optimistically. The server answers the sender with `ack {nonce, message}` and the broadcast also reaches the sender's socket as `message.created`. Both carry the same message id, and the client keeps messages keyed by id, so whichever arrives first wins and the pending entry is dropped on ack. Rejected: suppressing the broadcast to the sending socket (needs per-socket tracking across instances, and other tabs of the same user still need the message).
- 2026-10-21: Per-user message rate limit is a fixed window in Redis (`INCR` plus `EXPIRE NX` in one `MULTI`), shared by REST and WebSocket sends; general REST traffic uses `@fastify/rate-limit` with the same Redis. Fixed windows allow up to 2x the limit across a window boundary, which is fine for chat spam control. Rejected: sliding-window log (a sorted set per user, more memory and commands), token bucket in Lua (more code to own), and in-process counters (wrong as soon as there are two instances). The HTTP limiter fails open if Redis is down.
- 2026-10-21: User rows are upserted from the identity headers, with a 60 second in-process cache keyed by login. A request only touches the database when the cache is cold or the display name or avatar changed. The cache is per instance and bounded, and a changed profile is written through immediately because the cache entry only counts as a hit while the values match. Rejected: an upsert per request (a write on every API call) and a Redis-backed cache (another network hop to save a primary-key read).
- 2026-10-21: nginx sits between Tailscale Serve and the app and is the only published port (`127.0.0.1:8470`). Its config is a template rendered by the official image's envsubst step, restricted to `PROXY_*` variables so nginx's own `$variables` are never touched. The upstream is an `upstream` block so a second app instance is one more `server` line.
- 2026-10-21: In development, `DEV_AUTH_LOGIN` substitutes a fixed identity and skips the proxy secret. `loadConfig` refuses to start if it is set under any `NODE_ENV` other than `development`, so a stray variable cannot open a production deployment.
- 2026-10-21: Verified Tailscale Serve's header behavior before relying on it, from the v1.102.3 source (`addTailscaleIdentityHeaders`) and live tests: it deletes client-sent `Tailscale-User-*` headers on every request, sets them only for untagged user nodes, and RFC 2047-encodes non-ASCII names. Full write-up in `docs/security/trust-model.md`.
- 2026-10-21: The server's `message.created` broadcast carries the sender's nonce, so the sending client reconciles its optimistic copy whichever of `ack` or the broadcast arrives first.
- 2026-10-21: Harmony's containers opt out of the host's Watchtower auto-updates via label. Images are pinned and upgraded deliberately.
- 2026-10-22: Servers are called `guilds` in code, the database and the API (Discord's term), and "servers" only in the UI, so they are never confused with the backend server. Any signed-in user can create a guild and becomes its owner; `users.is_admin` is only an instance-level moderation override (it can delete/rename any guild and moderate messages) and is never required to create guilds or channels. The first user ever created is admin, decided inside the insert transaction under a Postgres advisory lock so two simultaneous first logins cannot both win; a migration backfill promotes the lowest existing id.
- 2026-10-22: Access is `channel_members` rows, kept in step with guild membership on purpose. Joining a guild inserts one row per non-private channel, creating a public channel inserts a row per guild member, leaving a guild deletes the user's rows for that guild's channels. That is write fan-out (cost grows with channels per guild on join and members per guild on channel create) in exchange for one uniform rule everywhere: "you can read a channel iff you have a row". Authorization, unread counts and the live-subscription check are single indexed lookups with no guild/visibility logic or joins. Rejected: deriving access from `guild_members` plus a visibility rule (every history, search, unread and WebSocket check would need the union of two sources, and the unread query would join guilds) and storing read state in a separate table (a second row per user per channel to keep in sync).
- 2026-10-22: Text channel names are unique per guild (`unique (guild_id, name)`); `guild_id` is null only for DMs, enforced by a check constraint together with the name and `dm_key` shape. A guild named "Harmony" is flagged `is_default` (one row, partial unique index); the migration creates it from existing data owned by the earliest user and moves `general` and its messages into it. Newcomers join the default guild on their first request; the very first user on an empty database creates it. Rejected: leaving new users guild-less (an empty first screen) and a hard-coded guild id.
- 2026-10-22: A non-member gets `403 forbidden` for anything that exists, `404` only for ids that do not. Hiding existence behind 404 would buy nothing because ids are sequential. Public channels can no longer be joined or left individually (that browse feature was dropped for guild membership); private channels can be left. Removing someone from a private channel needs the channel creator, guild owner or an admin who is a member of it; admins do not get read access to channels they are not in.
- 2026-10-22: Invite use-counting is one conditional `UPDATE ... SET uses = uses + 1 WHERE (expires_at is null or expires_at > now()) and (max_uses is null or uses < max_uses)`, inside the transaction that inserts the membership. Concurrent accepts serialize on the row lock, so `max_uses` cannot be exceeded; the membership insert runs first and a user who is already in the guild consumes nothing, which also makes double-clicks harmless. Tested with 10 simultaneous accepts of a 3-use invite. Rejected: read-then-write in the application (races) and advisory locks (the row lock is already enough).
- 2026-10-22: DM channels are created idempotently through `dm_key = "<minUserId>:<maxUserId>"` with a unique index and `INSERT ... ON CONFLICT (dm_key) DO NOTHING`, then a select on conflict. Two people starting a DM at the same moment get the same channel without any locking or retry loop. DMs are only allowed between users who share a guild, so a stranger cannot be messaged. Rejected: looking up "a channel with exactly these two members" (needs a group-by query and still races) and a separate DM table (the message, unread and WebSocket code would have to handle two kinds of channel).
- 2026-10-22: A per-user Redis topic (`harmony:user:<id>`), reference-counted per instance like channel topics. Events that concern a user rather than a channel (`channel.joined/removed/updated`, `guild.*`, `read.updated`, `mention`) are published once and reach every session of that user on every instance. `channel.removed` also makes the hub drop that user's live subscription to the channel, so losing membership ends delivery immediately and not only on the next `subscribe`. Rejected: pushing these over the channel topic (a sidebar needs events about channels the user is not subscribed to) and polling `GET /api/channels`.
- 2026-10-22: Unread counts. `GET /api/channels` computes, per channel the user is in, `max(id)` from `messages` (index `(channel_id, id desc)`), and two counts each from a subquery with `LIMIT 100`: messages with `id > coalesce(last_read_message_id, 0)` that are not mine and not deleted (range scan of the same index), and rows in `message_mentions` for me with `message_id > last_read` (new index `(user_id, message_id)`; the id bound is repeated on `message_mentions` because Postgres does not derive inequality bounds across a join). `count(*)` over a `LIMIT 100` subquery means a channel with 50,000 unread costs the same as one with 100, and `100` is reported as "100 or more". Guild badges sum the already-capped channel numbers and cap again. Read markers use `greatest(last_read_message_id, $new)` (`greatest` ignores NULL) so a stale tab can never move them back; the new id must be a message in that channel, otherwise a client could mark the future as read. People who join a channel start at its latest message. Rejected: exact counts (an unbounded scan per channel per page load), a denormalized unread counter (needs updating for every member on every message and drifts on delete), and a bound on `m.id` only without the `LIMIT`.
- 2026-10-22: Presence is a Redis sorted set per user (`harmony:presence:<id>`, member = connection id, score = expiry in ms) plus a set of user ids currently marked online. One Lua script performs add/refresh, remove and expire and returns whether the user flipped (`1` came online, `-1` went offline, `0` nothing). The marker set, not the ZSET size, is the source of truth, so the flip is decided atomically inside Redis and exactly one caller sees it, however many instances, tabs and sweepers race. Time comes from Redis `TIME`, so instances with skewed clocks agree on expiry. Each socket refreshes every 30 s with a 90 s TTL; every instance also sweeps all online users every 30 s, which turns a crashed instance's connections into one `offline` event within about two minutes. Transitions are published on `harmony:presence` and delivered to every connected client; `invisible` is published as `offline`. At this size that is a handful of users, so there is no scoping. At larger scale presence would be scoped to users who share a guild or DM with the viewer (maintain the viewer's set of peers per connection and filter on dispatch). Rejected: relying on the socket `close` event (misses crashes and network drops), Redis key expiry notifications (not delivered reliably and give no atomic transition), a per-connection key with TTL (cannot tell "last connection gone" atomically), presence rows in Postgres (a write per heartbeat), and a single elected sweeper (needs leader election; running the sweep everywhere and trusting the script's result is simpler and idempotent). Known gap: the Redis publish happens after the script returns, so two rapid flips from different instances could in theory be published out of order; clients refetch `GET /api/presence` on reconnect.
- 2026-10-22: Typing pings are ephemeral. A client frame is throttled with `SET key 1 PX 2000 NX` in Redis (one relay per user and channel every 2 s across all of the user's tabs and all instances) before the membership check, so a flood costs one Redis command. The relay is published on the channel topic and never stored; clients expire the indicator after about 6 s. All WebSocket frames also pass an in-process token bucket per socket (30 frame burst, 3 per second refill; extra frames get `rate_limited`, a socket that keeps going after 100 drops is closed with 1008). In-process is correct here because the budget is per connection, which lives on one instance. REST write limits (messages, reactions, uploads) stay fixed-window counters in Redis, shared by REST and WebSocket.
- 2026-10-22: Deleting a message is a soft delete (`deleted_at`). The row stays so replies keep their parent and reaction/mention/pin rows stay consistent; the API serves a tombstone (`deleted: true`, empty content, no attachments, reactions or mentions). Tombstones stay in history pages and backfill so keyset pagination has no holes and a client that missed the `message.deleted` event still learns about the delete when it reloads. Deleted messages are excluded from search, unread counts and pins. Files of deleted messages stay on disk until the guild is deleted. Rejected: hard delete (breaks reply links, loses audit trail) and removing the row from history (clients cannot tell a gap from a delete).
- 2026-10-22: Uploads stream to a `Storage` interface (`put/get/delete`; `LocalDiskStorage` writes `<key>.partial` and renames, so a failed or oversized upload leaves nothing). Size and SHA-256 are computed while streaming; the stream is piped with `pipeline`, not `.pipe`, so the multipart size-limit error reaches the writer and the partial file is removed. The content type comes from the file's magic bytes (`file-type`), never from the client; anything it does not recognise, including SVG and HTML, is stored as `application/octet-stream`. On download, only png/jpeg/gif/webp are `Content-Disposition: inline`; everything else is `attachment`, with `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and `Cache-Control: private, max-age=31536000, immutable` (the URL contains the immutable attachment id). Filenames are reduced to a basename without control, bidi or shell/markup characters. Access follows the message's channel (the uploader until attached; guild icons are visible to any signed-in user so invite previews work). Unattached uploads older than 24 hours are deleted by an interval job guarded by a Redis `SET NX PX` lock, which expires on its own so a crashed holder never blocks the next run; the job deletes rows first (never a row pointing at a missing file) and skips icons still referenced by a guild. nginx allows `client_max_body_size 11m` only on `location = /api/uploads`. Rejected: trusting `Content-Type` or the extension, serving SVG inline (script execution on the app origin), object storage in this phase (the interface is the seam for it), and a database lock for the cleanup job.
- 2026-10-22: Search uses Postgres full text with a generated, stored `tsvector` (`to_tsvector('simple', content)`) and a GIN index, queried with `websearch_to_tsquery('simple', q)`. The `simple` configuration only lowercases and splits on word boundaries: chat is multilingual and full of names, code and slang, and the `english` configuration would stem words ("running" matches "run") and drop stop words, which is wrong for non-English text and surprising for exact names. The cost is no stemming; users type the word they want. The membership join is part of the query, so messages from channels the caller cannot read can never match. Pagination is keyset on message id, newest first. Rejected: `ILIKE '%q%'` (sequential scan), an external search engine (another service to run for a homelab), and `english`.
- 2026-10-22: Mentions are `<@userId>` tokens written by the client. The server parses them, keeps only users who are members of that channel (and not the author), stores `message_mentions`, and notifies only newly mentioned users when a message is edited. Client-supplied token text is never trusted for notification; membership is checked on the server.
- 2026-10-22: History pages, search results and pins are hydrated in four queries regardless of page size (messages joined with author and reply parent, then reactions, attachments and mentions each fetched with `= any($ids)`). A test counts the SQL statements for a 1-message and a 31-message page and requires them to be equal.
- 2026-10-22: Web state lives in one zustand store (`apps/web/src/store`) with normalized records keyed by id (users, guilds, channels, per-channel history, outbox, typing, presence), and a single dispatcher that feeds it from REST and from `ServerFrame`s. `applyFrame` is a plain switch over the protocol's frame types, so the store is tested by feeding it frames, without React or a socket. Transient UI (toasts, drawers, jump requests) is a second tiny store so it cannot cause message-list renders. Rejected: Redux Toolkit (more ceremony for the same shape), React Query (the WebSocket is the source of truth for most data and cache invalidation would fight it), and per-hook `useReducer` state as in Phase 1 (could not drive sidebar badges or the title from events for channels that are not open).
- 2026-10-22: The client subscribes to every channel it can see, not only the open one, because channel events (and so unread counts) only arrive for subscribed channels. The dispatcher sends the first 15 `subscribe` frames at once and the rest at one per 400 ms, staying inside the socket's 30-frame bucket (3 per second refill), and the open channel goes first. `lastSeenId` is the newest cached message, else the channel's `lastMessageId`, so channels that were never opened get an empty backfill. Messages are cached only for channels that were opened; live events for others only update the summary, so a cache is never a partial list. On reconnect idle caches are dropped (edits and deletes are not in a backfill), the active channel refetches its newest page, and a backfill with `hasMore` drops the cache so the open view reloads.
- 2026-10-22: React Router (`react-router`, declarative `BrowserRouter`) for `/channels/:guildId/:channelId`, `/channels/@me/:dmId` and `/invite/:code`. The URL is the single source of truth for which guild and channel are open, so reload, back button and shared links work; the last channel per guild is remembered in localStorage only to pick where the guild rail goes. Rejected: keeping the selection in the store (no deep links) and a data router with loaders (data arrives over the socket, so loaders would add nothing).
- 2026-10-22: Message text is rendered by a small hand-written tokenizer (`lib/markdown.ts`) that produces a tree, and React elements are made from that tree. There is no HTML string anywhere and no `dangerouslySetInnerHTML`, so React's escaping is the only output path. Only `http:` and `https:` URLs become links (checked with `new URL`), `[text](url)` links are not supported at all, and nesting depth is capped. Rejected: marked + DOMPurify. It would be a larger dependency, would parse the full CommonMark surface (images, raw HTML, reference links) only to strip most of it again, and puts the safety of every message on a sanitizer configuration; a tokenizer that cannot express the dangerous constructs has nothing to bypass. The cost is that unusual Markdown (lists, headings, tables) shows as plain text.
- 2026-10-22: Mentions stay `<@id>` on the wire. The composer shows `@Name`, keeps a `@Name -> id` map for names picked from autocomplete, and converts on send with one regex over the known names (whole-word match, longest first); editing decodes the tokens back. Names the user typed by hand or edited are plain text, which matches the server's rule that only real members count. Known limit: two members with the same display name cannot be told apart in one message.
- 2026-10-22: Mobile is designed as the primary layout, below 900px: a full-screen chat, a left drawer holding the guild rail and channel list, a right drawer with members, and a bottom sheet for message actions (long-press instead of hover). Drawers are driven by `--pl` / `--pr` CSS variables (0 closed to 1 open) that the touch handlers write directly during a drag, so a swipe causes no React renders; an axis lock gives up on vertical gestures at once and the shell sets `touch-action: pan-y` so scrolling is never fought. Closed drawers are `inert`. The app root is `position: fixed` and sized from `visualViewport` (`--app-height`, `--app-top`), so the composer rides above the on-screen keyboard on iOS, where `100dvh` does not shrink; dialogs placed as sheets use the same variables. Enter inserts a newline on `(pointer: coarse)` devices and the send button sends. Rejected: a CSS-only responsive squeeze of the desktop grid, and a UI library (the touch behaviors are the product here).
- 2026-10-22: PWA through a web manifest and icons only (standalone display, theme color equal to the dark background token, SVG plus rasterized 192/512/maskable/apple-touch PNGs), with no service worker. Offline support would need a cache-invalidation story for the app shell and would not make chat useful offline; installability and the app-like window were the goal. The manifest cannot read CSS variables, so its colors are copied from the tokens.
- 2026-10-22: All colors, radii, spacing and fonts are CSS custom properties on `:root`; dark is the default and the light theme is the same tokens under `prefers-color-scheme: light`. Components contain no color literals (avatar tones are `--tone-N` variables picked by id hash), so Phase 5 user themes only have to override tokens. Radix primitives (dialog, alert dialog, dropdown menu, popover) provide focus handling, Escape and ARIA; everything visual is plain CSS.
- 2026-10-22: Development-only `dev_login` cookie: a dev-mode server (`NODE_ENV=development` and `DEV_AUTH_LOGIN` set) lets a browser choose its identity among `@example.com` logins, so one Playwright run can be several users. It is gated by the dev policy (production never builds one), restricted to a reserved domain and still subject to the allowlist and Origin check; see the trust model's "Development mode". Rejected: a header (browsers cannot set headers on WebSocket upgrades) and a separate test-only server build (a second code path to keep honest).
- 2026-10-22: Dev and e2e infrastructure never touch the production stack: a `harmony-dev` compose project (`compose.dev.yml`, tmpfs Postgres on 127.0.0.1:15432, Redis on 16379) and ports 18080 / 15173 for the API and Vite. The e2e suite lets Playwright start the API and Vite itself and runs in CI against service containers; the screenshots are a separate Playwright project (`E2E_SCREENSHOTS=1`) that seeds a fictional data set.

- 2026-10-22: Phase 3 (bot platform, backend). Bots are users: `users.kind in ('human','bot')`, `bot_owner_id`, and a synthetic login `bot-<id>@bots.harmony.invalid` (webhook authors: `webhook-<id>@...`). A check constraint ties the login suffix to `kind`, and the human auth path refuses any login under that domain. The consequence is that every foreign key (message author, reactions, `guild_members`, `channel_members`) and every authorization rule works for bots with no change: a bot added to a guild gets the same membership rows a person gets, and "a bot cannot read a guild it is not in" is the existing `403 forbidden`. The login carries the id, which only exists after the insert, so the row is inserted with a placeholder login and renamed in the same transaction. Rejected: a nullable login (every query that selects or displays `login` would need a null case, and `DirectoryUser.login` is a string everywhere) and a separate `bots` principal table with its own membership tables (a second authorization system to keep in step). Deleting a bot deletes its `bots` row (token, commands, deliveries) and memberships but keeps the user row, so messages it wrote keep their author.
- 2026-10-22: Bot tokens are `hb_<botId>_<43 char base64url>`. Only `sha256(secret)` is stored; the id in the token selects the row and `timingSafeEqual` compares the hashes, with a dummy comparison for unknown ids so existence is not timing-visible. A plain SHA-256 is right for a 256-bit random secret (nothing to brute-force, no reason to spend CPU per request); a password hash would only add latency. Tokens are shown once, rotation replaces the hash and revokes the old token on the next request because bot credentials are looked up on every request and not cached. `last_used_at` is written from an in-process map at most once a minute per bot per instance. The webhook and interaction tokens use the same format of secret and storage. Rejected: JWTs (cannot be revoked without a lookup anyway) and storing tokens encrypted (nothing needs the plaintext back).
- 2026-10-22: Bots authenticate with `Authorization: Bot <token>` on the same REST API and `/api/ws`. When that header is present the auth hook decides from the token alone: `Tailscale-*`, the proxy secret and the Origin check are never read, and a bad token is `401 invalid_token` with no fallback to a human identity (a request with a valid bot token plus `Tailscale-User-Login: admin@...` acts as the bot). That is safe because the Origin check exists to stop ambient credentials being replayed by a hostile page; an `Authorization` header is never ambient, a cross-site page cannot add one without a CORS preflight, and the app sends no CORS headers. The proxy-secret check is not required for bots so host-local scripts can use the nginx ingress, which has no secret. Rejected: accepting bot tokens only through the main proxied listener (host-local scripts would need Tailscale identity) and a separate `/bot-api` path or app (a second route table to keep identical).
- 2026-10-22: Routes declare bot access in route config: `scope: '<scope>' | 'any'`, `humanOnly: true`, or `public: true` (the path carries its own credential). A bot request needs the route's scope (`403 missing_scope`), `humanOnly` routes answer bots `403 human_only`, and a route that declares nothing is closed to bots (`403 bot_not_allowed`), so a route added later is safe by default. Human requests ignore scopes. Human-only for now: bot management, creating, changing and deleting guilds, channel management, invites, uploads, DMs, read markers, `PATCH /me`, webhook management and command invocation. WebSocket frames get the same treatment through a small frame-to-scope table. Rejected: default-open for routes that declare nothing (one forgotten annotation would hand bots a human endpoint) and scope checks inside the services (scattered, and invisible when reading the route).
- 2026-10-22: Bots have their own HTTP rate-limit bucket (`BOT_RATE_LIMIT_MAX`, default 600 per window, keyed `bot:<id>`) through the same `@fastify/rate-limit` instance by making `max` and the key depend on `request.bot`. Message and reaction limits keep applying per user id, which for a bot is its own. Rejected: exempting bots (a runaway bot could starve the instance) and sharing the human bucket (an integration would eat its owner's allowance).
- 2026-10-22: Incoming webhooks are Discord-compatible (`content`, `username`, `avatar_url`, `embeds[]`, plus Slack's `text`; `?wait=true`) so existing tools need no code. Each webhook gets a bot-kind user as the message author, so authorship foreign keys stay valid and the normal send path (`MessageService.send`, with a `source` argument that skips the membership check and the per-user limit) writes the message, the outbox row and the Redis broadcast. `username` and `avatar_url` are stored per message (`display_name_override`, `avatar_url_override`), not on the webhook, because they differ per call. The path token is the only credential: `public` route, constant-time hash compare, wrong id and wrong token both `401 invalid_token`. Per-webhook limit 30/min using a fixed window that also reports the remaining TTL for `Retry-After`. `@everyone` and `@here` are defused with a zero-width space. Embed limits are Discord's and enforced by zod; timestamps in Uptime Kuma's non-ISO format (`YYYY-MM-DD HH:mm:ss.SSS`, found in its source) are accepted and normalized, empty field values are accepted for the same reason. There are two embed schemas: a lenient input one (with the timestamp transform) and the stored/served one, because the response serializer encodes with zod and a one-way transform cannot be encoded (this was a real 500). Rejected: webhook messages authored by the creator (spoofs a person), a nullable author (breaks joins and every `Message.author`), and a per-webhook limit in process memory (wrong with two instances).
- 2026-10-22: Slash commands. Definitions are per bot per guild with a bulk overwrite (`PUT`), and a command name is unique per guild (`unique (guild_id, name)`), so `/roll` always has exactly one owner and the invocation needs no bot argument. Invocation (WebSocket `command.invoke` or `POST /channels/:id/commands`) validates options against the definition (shared `validateCommandOptions`, plus guild-membership checks for `user` and `channel` options), writes an `interactions` row with a hashed token and a 15 minute expiry, and calls the bot in the background; the invoker learns the result through their user topic. The bot is called with a 3 second deadline and answers `message` (posted as the bot), `message` with `ephemeral` (sent only to the invoker as `interaction.ephemeral` and never stored) or `deferred` (`interaction.pending`, then follow-ups to `/api/interactions/:id/:token/followup`, any number within 15 minutes). A timeout or any failure becomes `interaction.failed` with a reason. Rejected: holding the HTTP request or the socket frame open for the bot (the WebSocket handler is serial, a slow bot would block that user's other frames), persisting ephemeral answers (the point of ephemeral is that nothing remembers them), and Discord-style global commands (no use for them in a single-instance homelab).
- 2026-10-22: Request signing is `X-Harmony-Signature: v1=hex(hmac-sha256(secret, timestamp + "." + rawBody))` with `X-Harmony-Timestamp`, as in Slack and Stripe. The timestamp is inside the MAC and receivers reject skew over 5 minutes, which bounds replay. `sign`/`verifySignature` live in `@harmony/shared/signature` (a subpath export, because it needs `node:crypto` and the browser bundle imports the shared root) and the tests, the worker and the example bot all use that one implementation. The per-bot signing secret is shown once and can be rotated; it is stored in the clear because computing a MAC needs the secret. Rejected: a separate `packages/bot-sdk` (a new package and Dockerfile wiring for 40 lines) and asymmetric signatures (bots would need a key-fetch step for no gain on a private network).
- 2026-10-22: Outgoing events use a transactional outbox. The dual-write problem: a handler that commits a message and then calls the bot (or publishes to a queue) can crash between the two, so either the event is lost (commit, crash before send) or sent for a change that never committed (send first, then the commit fails). There is no way to make two systems commit together. The outbox makes it one system: the `event_outbox` row is inserted in the same Postgres transaction as the change (`MessageService`, reactions and guild membership now write inside their transactions), so the event exists if and only if the change committed, and `pg_notify('harmony_events','')` queued in that transaction is only delivered on commit. A separate worker then turns outbox rows into per-bot `event_deliveries` rows and delivers them. Delivery is at-least-once, not exactly-once, on purpose: the worker can crash after the bot returned 200 and before recording it, and a lost response looks the same as a lost request, so the only safe choice is to send again. Every delivery carries a stable `X-Harmony-Delivery-Id` so receivers can deduplicate; exactly-once would need the receiver to take part in a transaction with us. Rejected: calling bots inline after commit (the dual write), publishing straight to Redis pub/sub (no durability, no retries), and `LISTEN/NOTIFY` as the queue itself (messages are lost when no one is listening, and payloads are capped at 8 KB).
- 2026-10-22: The worker (`apps/server/src/worker.ts`, its own compose service from the same image) wakes on `LISTEN harmony_events` and polls every 5 seconds as the fallback for a dropped connection. Fan-out is one statement that claims outbox rows with `FOR UPDATE SKIP LOCKED`, inserts a delivery for each subscribed bot and stamps `fanned_out_at`. A bot receives an event only if it is a member of the guild, has the `events` scope, subscribed to the type, and (for message and reaction events) has `messages.read` and is a member of the event's channel, so private channels never leak to a bot that cannot read them. Delivery claims rows under a lease (`next_attempt_at = now() + 30 s`, `attempts + 1`) with `SKIP LOCKED`, so several workers never take the same delivery and a worker that dies mid-request simply lets the lease expire. Retries use exponential backoff with full jitter (base 2 s, cap 1 hour, 8 attempts, then `dead`); statuses are `pending`, `failed` (awaiting retry), `succeeded`, `dead`. The clock and delays are configurable (`DELIVERY_BACKOFF_BASE_MS` and friends, an injectable `random`), which is how the tests run it. Shutdown stops claiming and waits for in-flight deliveries. Health is a heartbeat file touched on every loop iteration. A retention pass deletes succeeded deliveries and outbox rows older than 7 days (dead deliveries go with their event, which also means a dead delivery cannot be redelivered after 7 days). Rejected: holding row locks across the HTTP call (a connection pinned per in-flight delivery), a Redis-based queue (a second source of truth that can disagree with the commit), and `event_outbox.guild_id` as a foreign key (it would couple event retention to guild deletion).
- 2026-10-22: SSRF protection for every request to a user-supplied URL (`interactionsUrl`, `eventsUrl`). `safeFetch` resolves the host once, refuses private, loopback, link-local, CGNAT (which includes tailnet addresses), multicast, unspecified and reserved IPv4 and everything outside global unicast in IPv6 (unwrapping IPv4-mapped, NAT64 and 6to4 forms), then connects to that exact address through the undici agent's `lookup`, so DNS rebinding cannot swap the destination between check and connect. No redirects, 64 KiB response cap, http(s) only. The WHATWG URL parser already normalizes decimal, octal and hex IP spellings before classification, and `localhost` names are rejected without DNS. URLs are validated when saved and again on every request. Instance-admin-owned bots may target private hosts only when they match `OUTBOUND_PRIVATE_ALLOWLIST`; the exception is checked per request against the owner's current `is_admin`. Rejected: a deny-list of a few known-bad addresses (misses encodings and new ranges), resolving and connecting separately (rebinding), following redirects after checking only the first URL, and filtering out private answers while still connecting to the public ones (an attacker controls which answer you get).
- 2026-10-22: Host-local integrations reach the app through a second nginx listener (container port 8081, published `127.0.0.1:8471`) that proxies only `POST /api/webhooks/`, `POST /api/interactions/` and requests whose `Authorization` header starts with `Bot`, 404 for everything else. It sets `X-Harmony-Proxy-Secret` and all known `Tailscale-*` headers to empty, so nothing on it can claim a human identity, and, as the Problems solved entry below warns, all `proxy_set_header` lines are at server level because a location that declares its own drops every inherited one. Routing on the header uses a `map` and `return 404` inside `if`, the one pattern nginx documents as safe. Rejected: reusing port 8470 (it stamps the secret), and exposing the app container directly to the host (no body limits or header scrubbing).
- 2026-10-22: The Phase 2a commit left out `apps/server/src/uploads`: the `.gitignore` entry `uploads/` (meant for the runtime upload directory) matches any directory of that name. The files existed only in the original checkout, so a clean clone did not build. The pattern is now anchored (`/uploads/`) and the directory is tracked.
- 2026-10-22: Phase 3b (bot platform, web UI). Embeds load their images (author and footer icons, thumbnail, image) and webhook avatar overrides straight from the sender's URL with `<img referrerpolicy="no-referrer" loading="lazy">`. The cost is that the image host sees the reader's IP address and user agent whenever a message is shown, which a sender could use to learn who is online. An image proxy would hide that, but it needs an authenticated fetcher with its own SSRF rules (the same work as `safeFetch`), a cache and a size limit, so it is left out until it is needed. The reader only ever contacts http(s) hosts: `safeHttpUrl` drops `javascript:`, `data:` and the like before anything becomes a link or an image, even though the server already rejects them, so a message stored by an older or buggier server cannot script the page. Rejected: proxying through the app now.
- 2026-10-22: Settings are routes (`/settings/user/...`, `/settings/server/:guildId/...`), not dialogs. A full-screen layout with a left nav on desktop and a drill-down list on phones needs real URLs for the phone's back button and for reload, and a bot's detail page is too long for a modal. Escape closes the whole screen from a window listener that ignores events a Radix dialog or menu already consumed (`defaultPrevented`). The old server settings dialog became the Overview page. Server settings are offered to the owner and to instance admins, matching who the API lets manage a guild.
- 2026-10-22: Slash commands are typed in the composer. `/` at the very start of the input opens a list from `GET /api/guilds/:id/commands` (prefix matches first); picking one swaps the textarea for a command chip and one field per option, so options are real inputs (a select for user, channel and boolean) instead of text to parse. Values are coerced and checked with the shared `validateCommandOptions` before `command.invoke` is sent, so most mistakes never reach the server. Typing `/name ` with a known name switches to the fields and carries the rest into the first string option.
- 2026-10-22: Ephemeral replies, "thinking" placeholders and command failures live in the store (`interactions`, per channel) and nowhere else, the same as the server treats them: never stored, gone on reload. A placeholder is replaced by the outcome with the same interaction id, cleared when that bot posts in the channel, and dropped at `expiresAt` by a one-second sweep in the open channel. A follow-up can send several ephemeral messages, so each gets its own key. Frame errors that echo a nonce no queued message owns (a rejected `command.invoke`) become toasts.
- 2026-10-22: Secrets are shown once by `RevealOnce` inside a dialog whose parent holds the only copy of the value; closing the dialog drops it. The value goes in a read-only textarea, not an input, so a 90 character webhook URL wraps on a phone instead of scrolling out of sight. The webhook URL is `window.location.origin` plus the returned path: the origin check already makes that the public origin. Links to the docs use `VITE_DOCS_BASE_URL` when set and otherwise name the file path, because the repository's URL is a deployment detail.
- 2026-10-22: A webhook author is one bot user that posts under many names, so message grouping compares the display-name and avatar overrides as well as the author id, and the header, avatar and BOT/WEBHOOK badge come from `messageIdentity`. Bots cannot be given an avatar from the UI: the API has no field for it (`CreateBotBody` and `UpdateBotBody` carry none), and adding one was outside this phase's rule of touching the backend only for bugs.
- 2026-10-22: Visual identity. Product feedback was that the UI read as a Discord clone, so the look changed and the information architecture (server rail, channels, chat, members, settings, drawers) did not. Direction: calm, warm, crafted, "a quiet room". Warm olive charcoal neutrals (canvas `#141413`, panels one step up) with a sage/jade primary accent for active state, focus, buttons, links and own mentions, and a secondary apricot accent kept for things that want attention: mention badges, unread dots, the "new" divider and messages that mention me. Presence colors are separate from both accents (the online green is yellow-green so it stays apart from jade). Light theme is warm paper (`#f7f4ee`) with the accents darkened; contrast of the pairs the UI uses is at least AA for text and 3:1 for dots (table in `docs/theming.md`). Layout signature: the rail, sidebar, chat and member list are separate rounded cards (16px, 8px gap) on a darker canvas; rail tiles are rounded squares with a ring and a short accent bar; avatars are squircles; the composer is a floating capsule; the hover toolbar is a pill; reply quotes get a curved connector; on phones the chat is full-bleed and the drawers and sheets are the same cards floating over a scrim. Typeface: Manrope (UI) and JetBrains Mono (code), both variable and self-hosted through `@fontsource-variable` so there are no third-party requests. Manrope is a geometric-humanist sans with open apertures and a slightly warm, rounded feel that suits the mood, stays legible at 14 to 15px, has a real range of weights (names at 750, timestamps quiet at 550 and smaller) and is not the system-ui or Whitney-like look that made the old UI feel generic. Rejected typefaces: Inter (the default of every app, no character), Nunito (too childish next to code and embeds), a serif for messages (beautiful, but long names, code and tables suffer). Token architecture for Phase 5: three layers, primitives (`--palette-*`, `palette.css`), semantic tokens (`--color-*`, `--radius-*`, `--space-*`, `--font-*`, `--density`, `--panel-gap`, `--avatar-shape`, `--shadow-*`, `tokens.css`) and components that read semantic tokens only. A unit test fails on any color literal or palette reference outside the two token files, and on a `var()` of a property nobody defines. Options are attributes on `<html>` (`data-theme`, `data-density`, `data-panels`) written by `applyAppearance()` and kept in `localStorage` for now; flat panels and three densities cost almost nothing because they only change tokens. Rejected: a CSS-in-JS or utility framework (a second styling system, and runtime cost, for a problem custom properties already solve), per-component theme props (themes would need to touch every component), gradients and glass effects (the brief was restraint, and they age badly), and keeping Discord's blue-gray with a new accent (it would still read as Discord at a glance). Full token reference: `docs/theming.md`.
- 2026-10-22: The desktop app (`apps/desktop`) is Tauri v2 and a thin shell: it loads the user's own Harmony server URL in its main webview and bundles only a small setup page ("Enter your Harmony server URL"). Rejected: Electron (about 150 MB because it ships its own Chromium, against roughly 10 MB when the app uses the WebView2 that ships with Windows, WebKit on macOS and WebKitGTK on Linux) and a PWA only (installable from Edge or Chrome already, but it has no tray, no autostart and no auto-update). Rejected: bundling the web client inside the app. Authentication is the Tailscale identity, so requests from the desktop app must leave through Tailscale on that PC and pass through Serve exactly like the browser's; loading the server's own origin means the `Origin` and CSRF checks pass unchanged with no CORS opening; and the UI is always the version the server runs. Tradeoff, accepted: there is no offline mode, and without a reachable server the window shows a browser error page (the tray menu's "Change server…" is the way back).
- 2026-10-22: Desktop bridge security. The remote page (the user's own Harmony server) gets IPC only through a Tauri v2 capability whose `remote.urls` is exactly the configured origin, added at startup from the stored URL (`app.add_capability`, built from the validated origin; the host is checked against `[A-Za-z0-9._-]` before it goes into a URL pattern) and when the setup page connects. The capability grants two app commands, `notify` and `set_badge`, and nothing else: no shell, fs, http, opener or core plugin permissions. Setup commands (`connect_server`, `get_server_url`) are in a separate capability with no remote URL, so only the bundled page can call them. Tauri 2.12 can add capabilities at runtime but not remove them, so "the old origin loses access" is enforced a second way: every command compares the calling webview's URL with the session's current origin and answers `forbidden` otherwise, and "Change server…" clears the session first. In-app navigation is restricted to the bundled page and the configured origin; anything else is opened in the system browser and cancelled in the webview, and `target=_blank` / `window.open` are denied and opened in the browser too. Rejected: `withGlobalTauri` or the shell/fs/http plugins (a compromised page would get far more than notifications), a restart on server change to rebuild capabilities (a restart races the single-instance plugin on Windows, and the command-level check already closes the hole), and trusting the web page to pass only safe arguments (the native side validates title, body and route lengths and characters; the route must be an absolute in-app path).
- 2026-10-22: Desktop notifications and the unread badge are decided in the web client (`DesktopBridge`, `lib/desktopBridge.ts`), not in Rust, because only the web store knows which messages mention me, which channel is a DM and what a mention looks like once decoded. The bridge is feature-detected (`window.__TAURI_INTERNALS__`) and a no-op in a browser. A notification carries a route (`/channels/<guild>/<channel>?message=<id>`); clicking it reaches the plugin's action handler, which focuses the window and dispatches a `harmony-desktop:navigate` event in the page, where the React router navigates and jumps to the message. Messages older than five minutes (a reconnect backfill) never notify. Rejected: the Web Notification API inside the webview (no click-to-focus control and permission prompts differ per platform) and polling from Rust (would need its own credentials and protocol client).
- 2026-10-22: Desktop releases and updates. `.github/workflows/release.yml` builds Windows (NSIS and MSI), macOS (aarch64 `.dmg`) and Linux (`.AppImage` and `.deb`) with `tauri-apps/tauri-action` pinned to a commit, signs the updater artifacts with a minisign key pair made with the Tauri CLI (private key and password only in GitHub Actions secrets and `~/.config/harmony-desktop/` on the admin's machine, public key in `tauri.conf.json`), and creates a draft release with `latest.json`. The updater endpoint is `releases/latest/download/latest.json` of this repository. No Authenticode or Apple certificates: SmartScreen and Gatekeeper warn on first run (documented in the README). The repository is private for now, so the unauthenticated update check gets a 404 until the repo is public or releases are mirrored; the check is silent and never blocks the app. The version has one source, `apps/desktop/package.json`; `tauri.conf.json` points at it and `version:sync` copies it into `Cargo.toml`/`Cargo.lock` (CI fails when they differ, and a release tag must equal `v<version>`). Rejected: universal macOS builds (double build time for a rare Intel Mac) and per-repo update proxies.
- 2026-10-22: Two app instances (`app1`, `app2`) behind nginx, defined from one YAML anchor that differs only in `INSTANCE_ID`, with `least_conn`, `max_fails=2 fail_timeout=10s`, `proxy_connect_timeout 1s` and `resolve`. `least_conn` because WebSockets are long-lived: round-robin balances arrivals, which drift apart as clients come and go, while `least_conn` balances connections that are open now (60 connections through the balanced listener split 30 and 30). **No sticky sessions are needed**: any instance can serve any client because every delivery goes through Redis (including to sockets on the same instance) and all state lives in Postgres and Redis (messages, read state, presence, rate limits, the user cache is only a TTL cache). A reconnecting client lands on whichever instance has the fewest connections, resubscribes with `lastSeenId` and backfills, so a dead instance costs a reconnect, not a session. Rejected: `ip_hash`/cookie stickiness (it would pin clients to a dead instance and hide the very property the Redis design provides), and a service mesh or Swarm/Kubernetes for two containers on one host. Separate decision: the load tests run in their own compose project, `harmony-load`, with its own network, volumes, image tag and 127.0.0.1 ports, and send `Tailscale-User-Login` and `Origin` themselves through the production nginx config; Tailscale Serve is bypassed and its cost is not in any number.

- 2026-10-22: Modules (Phase 5a). Everything beyond the core (reactions, pins, search, uploads, polls, coinflip) is a module registered through a narrow typed `ModuleContext` (`apps/server/src/modules`, contract in `docs/modules.md`); the web client has the mirror contract (`apps/web/src/modules`) with named UI slots. Customization (Phase 5b) builds on this: per-guild state, settings schemas and declared permissions are already stored. Rejected: handing modules the whole app or the Fastify instance (every module could then depend on anything, and none of it could be validated or disabled per guild); a plugin loader that scans a directory or `node_modules` (modules are code the operator ships, so an explicit list in `modules/index.ts` is auditable and typed, and adding one is one import line).
- 2026-10-22: Module migrations use one Kysely history table per module (`harmony_module_<id>_migration`) next to the untouched core `kysely_migration`, run core first and then modules in dependency order. Rejected: one combined provider with `allowUnorderedMigrations` (Kysely sorts by name, so ordering between modules would hang on names, and a module removed from the build makes the combined history "corrupted"), and name-prefixing (a later core migration would sort before applied module migrations). This deviates from the brief's two options by choosing a third, because it keeps the live database's applied migrations 0001 to 0013 exactly as they are and lets modules come and go. Cost: one table pair per module. `migrate` runs modules that `MODULES_DISABLED` turns off too, so the schema is always complete.
- 2026-10-22: Per-guild module state is a table (`guild_modules`) with defaults for a missing row (optional modules on), cached per guild in each process for at most five minutes and dropped immediately by a Redis pub/sub message on every write. Rejected: a database read per check (the send path would pay for it), and a cache with no TTL (one lost pub/sub message would leave an instance wrong forever).
- 2026-10-22: The message send path pays nothing for modules. A module's marker is a `messages.modules text[]` column (constant default, no table rewrite) written by the insert that already happens, decorators run only for rows that carry a marker and once per module per page, `DomainEvents.emit` is a map lookup when nobody listens and never awaits handlers, and module frames use the existing Redis topics (the hub tries the core schema first). `tests/integration/modules-hotpath.test.ts` records the SQL of a send with and without the shipped modules and requires the two to be identical (6 statements). Rejected: a `message_modules` side table (one more insert per module message and a join on every read), and making handlers awaited in the request (a slow module would slow every send).

Rejected: reusing the outbox (it is for bots, over HTTP, with retries) and Redis pub/sub (every instance would run every reaction; a module that wants cross-instance behavior publishes a frame, which already goes through Redis).

Rejected: the bot wins (a module could never be relied on), and rejecting at registration only for enabled modules (enabling a module later could silently shadow a bot). Rejected: a separate branding table (one row per guild anyway), storing the accent as text.

- 2026-10-23: An uploaded avatar replaces `users.avatar_url` (the picture every query and event already reads), and the sign-in provider's picture moves to `provider_avatar_url` with an `avatar_overridden` flag, so the upsert on each login keeps the override and "Reset" copies the provider picture back. Rejected: a `coalesce(profile.avatar, provider)` join in every place a user is selected (a dozen call sites, and a missed one shows the wrong face), and resolving the avatar in the client (messages would flash the old picture).
- 2026-10-23: Profile data rides on user lists and events, never on messages: `GET /api/users` gains `profiles` (summaries only for users who have something set), `user.updated` carries the same summary, and the full profile (bio, banner, roles, dates) is fetched when a card opens and refetched when a `user.updated` for that user arrives. Rejected: embedding profile fields in every message author (bigger payloads on the hot path, stale copies in history) and fetching a profile per rendered message.
- 2026-10-23: `user.updated` goes to the audience (the user, everyone sharing a guild, everyone sharing a DM) found with one query and published through a pipelined Redis batch of 500. Rejected: a per-recipient publish loop (a round trip each), a new Redis topic per guild that every socket would subscribe to (the hub subscribes per user and channel today), and debouncing (a second of delay in a rare event is not worth the state; rapid edits are already one PATCH each).
- 2026-10-23: Statuses expire lazily (a read treats an expired status as empty and clears it) and by a periodic sweep guarded by a Redis lock, which emits `user.updated`. Rejected: a timer per status (lost on restart, multiplied by instances) and relying on the sweep alone (a card would show an expired status for up to one interval).
- 2026-10-23: Custom emoji tokens are `<:name:id>` / `<a:name:id>`. The server rewrites them on send and edit using a per-guild in-process map invalidated over Redis (`harmony:emoji:invalidate`, like permissions), plus a small cache of single ids for emoji from other servers; messages without a `<` never touch it, so the six-statement send test is unchanged. Unusable tokens become `:name:` text rather than a rejection, so a paste from another server never fails a send. Rejected: validating in the client only, a query per token, and storing a resolved form separately from the content.
- 2026-10-23: Emoji upload reuses `POST /api/uploads` and then `POST /api/guilds/:id/emoji` with the attachment id, like guild icons, so magic-byte sniffing, headers and the orphan sweep stay in one place; image bytes are served from `GET /api/emoji/:id/:filename`, readable by any signed-in user. Rejected: a second multipart endpoint, and making emoji images attachments of a message (access would follow channel membership and break cross-server display).
- 2026-10-23: Emoji data and token rules are core (`guild_emoji`, `EmojiService`, like reactions), while management (routes, `manage_emoji`, the settings page) is the optional `custom-emoji` module. Switching the module off stops management and stops tokens from being accepted in new messages, and existing messages keep rendering. Rejected: making all of it a module (a module cannot sit on the message send path without a new hook), and keeping it core (a server that does not want emoji could not hide the page).
- 2026-10-23: Perks are core, not a module: they are instance-wide (not per guild), checked by core paths (uploads limit, theme limit, profile) and a module's per-guild switch would be the wrong scope. Effective perks are `PERKS_DEFAULT` plus `user_perks`, cached per user in process and invalidated over Redis. Rejected: a per-guild perk module, a boolean `is_nitro` flag (cannot express "animated avatars but not banners"), and payment hooks (out of scope; the layer is admin-granted on purpose).
- 2026-10-23: The avatar crop is a client-side canvas (drag, zoom, 256 px PNG output), with the geometry in a small pure module that is unit tested. Animated GIF and WebP avatars skip the crop (a canvas flattens them) and are validated on the server. Rejected: a cropping library (a dependency for 60 lines) and server-side resizing (it would mean decoding untrusted images on the server).
- 2026-10-23: Animated detection reads only headers (GIF block walk, WebP VP8X flag, APNG acTL) from a file the server already stored, capped at 8 MB for avatars and 256 KB for emoji. Rejected: decoding with an image library (attack surface and CPU for a yes/no answer).
- 2026-10-23: nginx's upload body limit rose from 11m to 51m so `larger_uploads` (default 50 MiB) is reachable behind the proxy; the app still enforces the per-user limit while streaming and the 1m default applies everywhere else. Rejected: leaving 11m (the perk would silently not work in the Docker deployment).
- 2026-10-23: Presence is scoped and batched (Phase 6). A user's presence goes to one Redis topic per guild and per DM they are in (`harmony:presence:guild:<id>`, `harmony:presence:dm:<channelId>`); a socket subscribes to its user's topics, loaded with one query at connect and kept live from the `guild.joined`/`guild.removed`/DM `channel.joined` events. Each instance coalesces per topic for `PRESENCE_BATCH_MS` (1 s) and sends one `presence.batch` frame per topic; the shown status lives in a Redis hash changed atomically with the online set, so snapshots need no database. `GET /api/presence` lists only people sharing a guild or DM with the caller (closes a small privacy leak, see the trust model). Rejected: filtering on every instance at receipt (needs memberships of users it has no sockets for, and a cold permission cache would mean queries per event), per-socket batch state (memory grows with sockets times audience; a 10,000-member guild would hold tens of millions of entries), keeping `presence.updated` on the socket (nothing needs it).
- 2026-10-23: Unread counts left as they were. The `LATERAL`/`ORDER BY` rewrites do not change the plan (primary-key walk, 23.9k buffer hits, 160 ms at 600k rows in a few dense channels), and the one thing that did (a covering index) costs every send a second index write. Analysis and a proposed counter design are in docs/performance.md. Rejected for now: a new index on `messages`, stored counters.
- 2026-10-23: Windows desktop app is frameless. The native title bar is drawn in the user's Windows accent color (bright green in the product owner's screenshot) and cannot be themed, so the window is built with `decorations(false)` and `shadow(true)` (Windows 11 keeps the rounded corners and drop shadow), a 400x500 minimum and the default theme's canvas color as the window background so the first paint is not white. macOS and Linux keep their native decorations. Rejected: setting the window theme (Windows still paints the accent color when the user's "Show accent color on title bars" setting is on), and `titleBarStyle: Overlay` (macOS only). macOS overlay was not done: it needs the page to leave room for the traffic lights and the benefit is small.
- 2026-10-23: The title bar is rendered by the web client, not the shell, because the window loads the server's origin. `TitleBar` (apps/web) appears only when `hasCustomTitleBar()` is true (Tauri present and the user agent says Windows); it sets `data-titlebar` on the root, which gives `--titlebar-height: 32px` that `.app` subtracts, so the browser and PWA are untouched. It sits on `--color-bg-canvas` so it melds with the floating panels, uses theme tokens only, and its height does not follow density (caption buttons are 46x32 like every Windows app). The bundled setup page draws the same bar in plain TypeScript, since it does not load the web client. Dragging uses a `mousedown` handler (`detail === 2` toggles maximize), not `data-tauri-drag-region`, so the page needs no event or window plugin permissions.
- 2026-10-23: Window IPC is five custom, argument-free commands (`window_minimize`, `window_toggle_maximize`, `window_is_maximized`, `window_close`, `window_start_dragging`) instead of the core `core:window:allow-*` permissions. Core permissions take a window `label` argument and cannot be scoped by caller beyond the capability's window list; our commands act only on the calling `main` window, check the caller's URL against the session on every call like `notify`, and `window_close` goes through the same `CloseRequested` handler as the native button (hide to tray). The maximized state is read after each DOM `resize` event instead of subscribing to a window event, which would need `core:event` permissions.
- 2026-10-23: Snap layouts (the Windows 11 hover flyout on the maximize button) are lost with custom caption buttons: Windows only shows it for a window-owned `HTMAXBUTTON` hit-test result, and a WebView2 child window covers the whole client area and swallows `WM_NCHITTEST`. Known workarounds (tauri-plugin-decorum and similar) subclass the window procedure and overlay a transparent hit-test region over the button; that is unsafe code on a platform I cannot run here, so it is not implemented. Win+Z, dragging to a screen edge and the keyboard snap shortcuts still work. Accepted tradeoff.
- 2026-10-23: Scrollbars are themed once in `base.css`: `scrollbar-width: thin` and `scrollbar-color` from tokens, plus `::-webkit-scrollbar` rules inside `@supports not (scrollbar-width: thin)`, because Chromium 121 and later ignores the pseudo-elements entirely when the standard properties are set. Rejected: pseudo-elements only (a hover state is not worth ignoring the standards). The settings page header is now sticky with the panel background and the scroll container has `scroll-padding-top`, so section headings are no longer cut by the rounded top edge.
- 2026-10-23: Setup page discovers servers through the `tailscale` CLI (`status --json`), run directly with fixed arguments and a timeout, never through a shell. Install locations are checked before `PATH` so a planted binary earlier on `PATH` is not preferred. Peers are probed over verified TLS at `:18470` and `:443` (plus an optional port) with the same `/healthz` check as manual entry, at most 16 at a time, 1.5 s each. Nothing connects without a click, even with a single result. Devices that are not provably the user's own (another member's, shared in from another tailnet, tagged) get a "Not your device" badge and a "Connect anyway" button. Rejected: the local API socket (platform-specific paths and auth), scanning ports on every address (noisy, and Tailscale already says which peers are online).
- 2026-10-23: "Disconnect" and "Change server..." are one flow (`window::disconnect`): the session origin is cleared, the stored server address is cleared (so the next start shows the setup page too) and the window shows the setup page. The recent-servers list is kept and no WebView data is touched, so reconnecting restores cookies and local storage. It is in the tray ("Disconnect / switch server...") and in a menu next to the title bar's name; the second needs `allow-disconnect-server` for the remote origin, which can only send the user back to the setup page. "Forget" removes a list entry only. A "clear local data for this server" option was omitted: Tauri 2 only exposes `clear_all_browsing_data` (every origin), and per-origin clearing would need WebView2's DevTools protocol through platform code. Rejected: wiping data on disconnect (loses drafts and settings the user expects back).
- 2026-10-23: Switching Tailscale accounts uses `tailscale switch --list` and `tailscale switch <id>`. The id from the page is checked against a fresh listing before it reaches the command line, so no free-form text becomes an argument; the page asks for confirmation first and, on failure (for example no permission to switch), shows Tailscale's own message and points at the tray menu. All of these commands are local-page only.

## Problems solved

- `pnpm fetch` failed in Docker with `ERR_PNPM_IGNORED_BUILDS`: pnpm 12 refuses to continue when dependencies have unapproved install scripts. Fixed by declaring `allowBuilds` in `pnpm-workspace.yaml` (esbuild allowed; cpu-features, protobufjs and ssh2 from Testcontainers denied).
- ESLint crashed at startup with "typescript-eslint does not support TS 7.0". Pinned TypeScript to 6.x across the workspace.
- `Migrator` and `FileMigrationProvider` are no longer exported from the `kysely` root in 0.29; they are imported from `kysely/migration`.
- Kysely's `FileMigrationProvider` dynamic-imports migration files, which needs file URLs under ESM, and the production image only has compiled JS. Migrations are compiled to `dist/migrations` by a second `tsc` pass, and the migrator uses that folder when present, else `migrations/` from source.
- A rejected WebSocket upgrade (bad Origin, no identity) left its socket open, so `app.close()` hung until the test hook timed out. `@fastify/websocket` marks a request as an upgrade in its own `onRequest` hook and destroys the raw socket in `onResponse` only if that flag is set; my auth hook, registered earlier, threw before the flag was set. Registering the websocket plugin before the auth plugin fixed it.
- nginx returned 403 `proxy_required` for every proxied request even though the secret was rendered correctly: `proxy_set_header` directives are inherited by a location only if the location declares none, and the WebSocket location declared two. All `proxy_set_header` lines now live at server level and the locations add none.
- The production image crashed on start with `Cannot find package 'ws'`: it was only a dev dependency, but the hub imports it at runtime. Moved to `dependencies`.
- The nginx integration test first put the real app behind nginx with `host-gateway`; every proxied request timed out because the host firewall drops traffic from containers to host ports. The test now runs the real template against a second nginx container that echoes the headers it received, on a private Docker network, which exercises the exact thing under test (what nginx forwards, and the body-size limits per location) without depending on host networking.
- After `docker compose up -d --build` the new `/api/uploads` location was not live: nginx only renders its template at container start and the template is a bind mount, so compose saw no change and kept the old container. `docker compose restart nginx` is needed after editing the template.
- Long-pressing a message opened the action sheet, which closed again when the finger lifted: the release produced a click on the full-screen overlay, which counted as an outside tap, or landed on a sheet action. The sheet now ignores outside interaction and pointer events for its first 600 ms (`graceMs`, a CSS `guard` animation for `pointer-events`). Found by the mobile e2e test, not by the desktop-sized screenshots.
- `**bold *italic***` rendered as bold text with stray asterisks: the search for a closing `**` stopped at the first two characters of the closing `***`. A two-character closer now closes on the last two characters of a longer run.
- The left drawer's shadow showed as a dark strip on the screen edge while the drawer was closed (translated off-screen but its blur reaches in). The shadow is only applied while a drawer is open or being dragged.
- The Playwright image's `system-ui` resolves to a font without a bold face, so every screenshot looked flat. The screenshot run injects a font that has bold; real devices are unaffected.
- A Playwright worker restart after a failed test re-ran `beforeAll`, which seeded the whole data set twice (duplicate server in the rail). Fixed by making the failing steps robust and resetting the database before each screenshot run.
- React 19's lint rules (`react-hooks/refs`, `set-state-in-effect`) rejected patterns that are common in older code, such as mirroring state into a ref during render and resetting state inside an effect. Refs are now updated in effects, and reset state is derived or reset by remounting.
- `useUi((s) => s.setDrawer)` tripped `unbound-method` because the store interface declared methods; actions are declared as function properties.
- The response serializer returned 500 for webhook messages with embeds: `fastify-type-provider-zod` encodes responses with zod, and a schema with a one-way `transform` (Uptime Kuma timestamp normalization) cannot be encoded. Inputs and served output now use separate embed schemas.
- `/api` without a trailing slash on the new nginx listener answers a 301 to `/api/` using the request's `Host` (which a test client then followed to the internal port); it reveals nothing and the target is a 404, so it was left alone and the probe removed from the test.
- The Phase 2a commit left out `apps/server/src/uploads/`: the ignore rule `uploads/` meant for local upload data matched any directory with that name, so CI failed on a clean clone while local builds passed. Anchored the rule to the root (`/uploads/`). Lesson kept: a green local run is not enough, wait for CI on the pushed commit.
- The first mobile screenshot of a bot's delivery log showed the settings close button painted over the scrolled card text: the button is absolutely positioned in the layout and the page scrolls underneath it. On phones the page header is now sticky with an opaque background and reserves room for the button.
- `mergeUsers` copied only id, login, name and avatar, so a bot's `isBot` flag was lost the first time its message passed through the store and the BOT badge vanished from member lists and later messages. It now keeps and compares the flag; a store test covers it.
- Webhook messages from one webhook but different `username`s were grouped under the first sender's name and avatar, because grouping looked at the author id only. Grouping now includes the per-message overrides.
- The e2e check for a `javascript:` embed link could not be written against a real webhook: the server validates `url` as http(s) and answers 400. The client guard is therefore covered by component tests that feed the renderer the hostile values directly.
- After the restyle every `<button>` rendered with different letter and word spacing from surrounding text, and 1x screenshots showed run-together words ("BookClub", "Todayat"). The user-agent stylesheet resets `word-spacing` and `letter-spacing` on form controls, and Manrope's space glyph is narrow at small sizes. The reset now inherits both on controls and the body adds a small `word-spacing`. Found in the first desktop screenshots, invisible at the phone's 3x scale.
- The shared `:focus-visible` outline (2px accent, offset) drew a hard square ring inside the composer capsule and the slash-command option pills, which already show a focus ring on the container. Inputs inside such containers now opt out of the outline. Found by the mobile keyboard and slash-option screenshots.
- Choosing the compact density changed message spacing but not list rows: `--tap-min` was enforced as a 36px minimum on desktop as well. Row minimums now use `--tap-row`, which is 0 on mouse devices and 44px on touch, so compact is compact on desktop and touch targets are never shrunk.
- Manrope is wider than the old system font, so the delivery log's "Redeliver" buttons were clipped by the table's horizontal scroll at 1440px. Cell padding was tightened and the settings content column widened to 800px.
- The pins popover screenshot captured the popover halfway through its fade-in, so message text showed through it; the screenshot run now waits for the animation. Found by looking at the image, not by any test.
- `gh workflow run release.yml --ref <branch>` answered 404 while the workflow only existed on a branch: `workflow_dispatch` needs the file on the default branch. The release workflow is exercised on a branch by pushing a throwaway `v0.1.0` tag instead (tag runs use the workflow file at the tag's commit); the draft release and the tag are deleted afterwards.
- `pnpm install` rewrote `pnpm-workspace.yaml` with a `minimumReleaseAgeExclude` list for `@tauri-apps/cli` 2.12.4, which was a day old. That silently weakens the supply-chain policy for everyone, so the file was restored and both Tauri npm packages are pinned to 2.12.3, the newest release old enough to pass.
- `cargo check` failed on Linux for `set_overlay_icon`: the taskbar overlay exists only in Tauri's Windows build. The overlay code (and its pixel helper) is compiled for Windows only, with a lint allowance for the helper that its test still uses elsewhere.
- After `docker compose up -d --build app` on the live stack every request returned 502 until nginx was restarted: nginx resolves upstream hostnames once at startup, the recreated container had a new IP, and nginx kept the old one. With two app instances this would hit every deploy and every failover. Fixed in the upstream block with `resolver 127.0.0.11 valid=10s`, a shared `zone`, and `server app1:8080 resolve` (open source nginx 1.27.3+; the pinned 1.27.5 image supports it). Verified by recreating app1 onto a different address without touching nginx: 85 of 85 REST probes stayed 200 and traffic returned to the new app1 4.3 s after it was healthy.
- After `docker kill`, clients on the dead instance waited the full `proxy_connect_timeout` before nginx tried the other one (nothing answers on the address, so there is no refusal): p50 reconnect 2.26 s at 2 s, bimodal 0.3 s or 1.3 s at 1 s. The default would have been 60 s. `proxy_connect_timeout 1s` plus `proxy_next_upstream_tries 2` keep it bounded.
- Message throughput saturated at about 700 msg/s while the app processes were mostly idle: each send issued 12 Postgres statements and woke the outbox worker once per NOTIFY (about 2.7 events per fan-out query). Cutting a send to 6 statements, one-statement outbox insert plus NOTIFY, a 50 ms worker batch window and per-event instead of per-socket serialization raised the ceiling to about 1,010 to 1,020 msg/s with the same CPU caps (`docs/performance.md`).
- A failover test client lost 85 messages: on `hasMore: true` it re-subscribed with the highest id it had seen, which skipped the middle of the gap because live messages had arrived meanwhile. The documented behaviour (reload over REST) fixes it.
- Not fixed, found while measuring: the unread-count subquery plans a scan of the whole `messages` primary key for channels with little unread, so `GET /api/guilds` took 170 to 350 ms with 600,000 messages in the table; it grows with total messages. Details in `docs/performance.md`.
- Deploying the two-instance topology left every request at 502: the nginx configs are bind-mounted, so `docker compose up` did not recreate the proxies and they kept the old upstream (`app`, which no longer existed). `scripts/deploy.sh` now restarts the proxies whenever `deploy/nginx` changed since the last deploy.
- The hot-path test failed on its first run: the test module's `message.created` handler asked the per-guild state whether it was enabled, which loads `guild_modules` once per guild, so the statement list differed from the baseline. Handlers run off the request path, but they do cost a query the first time, so the guarantee is stated for modules that do not register such a handler and the test uses the shipped modules.
- Frames from modules broke the test WebSocket client and would have been dropped by the hub: both parsed every frame with the closed core union. The hub now tries the core schema first and falls back to the module frame shape, the web client keeps two listeners, and the test client records module frames separately.
- Method-style members in the new interfaces (`close(): void`) tripped `@typescript-eslint/unbound-method` as soon as a context was destructured. The contract types use function-typed properties instead, and route plugins are plain functions rather than async ones (an `async` plugin without an `await` fails `require-await` in every module).
- Two existing tests assumed the command list held only a bot's commands (one polled until it counted two, so it went on before the bot had registered). They now count the bot's commands, since built-in commands appear in the same list.
- A switch that is controlled by the server round trip cannot be driven with Playwright's `uncheck()`, which expects the state to flip at once; the e2e clicks it and waits for the new state.
- Phase 5b halved fan-out capacity (900 msg/s target: about 750 to 815 achieved, p50 above 1 s) with unchanged statement counts and a good `EXPLAIN ANALYZE`. Cause: the message re-read gained two joins (`channels`, `guild_members`) for the author's nickname, which more than doubled the planning time of a query that is planned on every send (0.35 against 0.14 ms warm; 1.36 ms mean under load with `track_planning`), and Postgres sat at its 2-CPU cap. Found by comparing `pg_stat_statements` with and without planning, and confirmed by an image with the nickname replaced by a constant (back to 897 msg/s). Fixed by serving nicknames from the in-process permission cache. The first version of the fix deadlocked the connection pool under load (transactions waiting for a second connection to load the guild while holding their own); readers inside a transaction now use the cache without waiting and callers warm it first. Lesson: a first `EXPLAIN` in a new session pays about 3 ms of cold catalog caches, so measure planning repeatedly in one session; and a hot-path query change needs a send-rate run, not just a plan.
- The mobile role editor showed two back arrows (the page's and the editor's). The page header's arrow now returns to the role list while a role is open, and the editor has none of its own; screenshots retaken.
- Phase 5c-1: the first theme-editor screenshots showed the controls squeezed into a 300px column (the settings page is capped at 800px and the editor wants two columns), swatches stacked above their hex fields, and on phones the pinned preview covering a third of the screen. The editor page is wider, each color is one row, and the phone preview is capped at 20% of the height.
- A preset chosen and then reloaded within 300 ms was lost, because settings are saved after a debounce. Pending changes are now sent with `keepalive` when the page hides.
- `outline-width` computes to `3px` even when `outline-style` is `none`, so the safe-mode e2e check asserts the style instead.
- Screenshots that took an appearance through localStorage leaked between contexts once appearance moved to the server (the same user in the next context inherited it); the screenshot spec now sets appearance through the API before every visit.
- After 5c-2 the full integration suite hung (120 s hook timeouts across unrelated files) while each file passed alone. `createTheme` checked the `extra_themes` perk inside a transaction holding a `FOR UPDATE` row lock: concurrent creates for one user filled the 10-connection pool waiting on that lock while the lock holder waited for an 11th connection for the perk lookup. Same class of bug as the Phase 5b nickname deadlock; the rule now is to resolve anything that needs the pool before opening a transaction. The suite went from hanging to ~15 s.
- The orphan-cleanup tests in two files raced for the same global Redis lock key once a second file started running a cleaner. `UploadCleaner` takes an optional `lockKey`; each test file uses its own.
- The e2e "editing a profile updates another user's open popover live" failed in CI for two reasons. The test clicked the first author named "alice" in the shared `#general`, which in the full suite was the Alice from `messaging.spec.ts`, so it opened someone else's popover; it now matches this run's unique name. Separately, `ProfilePage` refetched after its own save (the `user.updated` it receives bumps the profile version) and overwrote the bio being typed with the stored empty value, so the bio blur saved nothing. The refetch now replaces only fields not edited since the last load (`ProfilePage.test.tsx`). The `read ECONNRESET` / `write EPIPE` lines in the log are Vite proxy noise; they also appear in passing runs.
- Phase 6 first measurement looked like a fan-out regression (p95 67 ms against 9 to 13 ms recorded earlier). Re-running BEFORE and AFTER back to back on fresh stacks gave the same spread for both (17, 58, 67 ms against 26, 61, 65 ms), so I did not attribute it to presence; the cause of the drift from earlier days was not found.
- Every load user is auto-joined to the default guild, so the first "many small guilds" world was really one giant guild. Noticed because AFTER's presence update counts were ten times what 100-member guilds would give. Both shapes are now measured and labelled (`giantdefault` result files), the scoped one by removing the users from the default guild (`loadtest/scripts/detach-default-guild.sql`).
- The load watchdog killed the BEFORE 5,000 run twice at a host load average of 12.0 and 12.4 (the host has 12 threads and 25 other containers); the limit is now `WATCHDOG_LOAD`, set to 16 for all Phase 6 runs. A `| head -2` on a run script also killed one run through SIGPIPE; repeated.
- In the hub, the gate that holds a socket's user events while its presence topics load was never set (the task ran synchronously); caught in review before any test failed, since no test races a membership change against connect.
